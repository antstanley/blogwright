## Steps

- [x] Verify against the AWS reference **before writing** that `IcebergDestinationDescription` carries `CloudWatchLoggingOptions` in a `DescribeDeliveryStream` response, and that `IcebergDestinationUpdate` accepts `CloudWatchLoggingOptions` among the fields `UpdateDestination` takes. Both are load-bearing and neither is catchable by a transport test: these tests assert the body the implementation itself constructs, and a wrong key spelling passes every one of them. This is task 34's established rule for this client.
- [x] `packages/analytics/src/aws/firehose.ts:94` - `IcebergDestinationInput` gains `readonly logGroupName: string` and `readonly logStreamName: string`, both **required**. The plugin builds exactly one shape of destination and always enables logging, so an optional field would model a call site that does not exist.
- [x] `:304` - `buildIcebergDestination` emits `CloudWatchLoggingOptions: { Enabled: true, LogGroupName: input.logGroupName, LogStreamName: input.logStreamName }`. Both `createDeliveryStream` and `updateDestination` go through this builder, so an existing stream is reconfigured in place: `UpdateDestination` keeps the stream's ARN, and the CloudFront log delivery pointed at it is untouched.
- [x] `packages/analytics/src/nodes.ts:1972` - `firehoseDestination` supplies both fields, the group name from task 03's shared helper and the stream name from `DESTINATION_DELIVERY_STREAM`. Not a second literal: the node that creates the group, the role that grants on the stream and the destination that names both must be one string each.
- [x] `:1902` - `applyFirehoseRolePolicy` gains a fifth statement, `logs:PutLogEvents` on `arn:aws:logs:<ANALYTICS_REGION>:<account>:log-group:<firehose log group>:log-stream:DestinationDelivery` - a concrete ARN, no wildcard, the discipline the other four keep. Correct the doc at `:1898`: Kinesis and KMS are still grants this pipeline does not need; CloudWatch Logs no longer is.
- [x] `packages/analytics/src/aws/firehose.ts:226` - `DestinationDescriptionResponse`'s `IcebergDestinationDescription` gains `CloudWatchLoggingOptions?: { Enabled?: boolean }`; `:174` - `DeliveryStreamStatus` gains `readonly loggingEnabled?: boolean | undefined` beside `appendOnly`; `:419-427` - `describeDeliveryStream` reads it back off the live destination and spreads it only when defined, exactly as `appendOnly` is. Read back rather than assumed, for the reason `appendOnly` is: it is what the node compares to decide whether to reconcile, and assuming a stream this plugin created carries the configuration this plugin sends is the assumption this whole task exists to break.
- [x] `packages/analytics/src/nodes.ts:2032` - `recordStream` records it through the same `recordOptional` that clears a stale entry when the describe stops reporting one, and its doc at `:2019-2026` stops describing a single compared flag.
- [x] `:2336` - **the guard becomes two conditions**: return only when `appendOnly === STREAM_APPEND_ONLY` **and** `loggingEnabled === true`. `undefined` matches neither, which is already this node's stated rule and is what makes an existing stream reconcile. Rewrite the comment above it to state both conditions and why the second one exists.
- [x] Correct the two pieces of prose that assert the old single-condition behaviour: the `read()` comment at `:2305-2315` ("it branches on the recorded `AppendOnly` flag alone, so a `CREATING_FAILED` or `DELETING` stream whose flag already matches is reconciled with zero AWS calls") and the `UpdateDestination` log line at `:2361`, which reads `AppendOnly <recorded> -> <desired>` and would tell an operator "AppendOnly true -> true" on every logging-only reconcile. Name what actually differs.
- [x] Convert the existing zero-call case at `packages/analytics/src/nodes.test.ts:3131` rather than deleting it. Its fixture is `withRecordedStream(ctx, { appendOnly: true })` - a stream that is append-only with no recorded logging, which is precisely `staging-iamstan` and every other stream this plugin has created. It becomes the **reconciling** case: `update()` issues `UpdateDestination`. Add a new zero-call case whose fixture is `{ appendOnly: true, loggingEnabled: true }`. Both directions, or the guard is only half asserted: a guard that never returns early passes the first case alone.
- [x] Assert the fallback does not fire for a logging-only delta: the logging-only case issues `UpdateDestination` and no `DeleteDeliveryStream`/`CreateDeliveryStream` pair, and logs no "was refused" warning. `IcebergDestinationUpdate` documents `CloudWatchLoggingOptions` among the fields it accepts, so the fallback should not fire - but if it ever did, the cost is a replaced stream, a new ARN and a repointed CloudFront delivery for a log setting.
- [x] Widen the fixtures the new field touches: `destinationWith` (`:2443`) carries a `CloudWatchLoggingOptions` value, the create case's whole-state `toStrictEqual` (`:3088-3095`) gains `loggingEnabled: true`, and the `analytics-firehose-role` policy case counts five statements rather than four while still asserting no `*` resource.
