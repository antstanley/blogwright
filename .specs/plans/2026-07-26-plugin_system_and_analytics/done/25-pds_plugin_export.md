## Steps

- [x] Create `packages/pds/src/plugin.ts` exporting a `Plugin` with `name: 'pds'`, a one-line `description` distilled from the `USAGE` pds block at `packages/cli/src/cli.ts:33-47`, `configKey: 'pds'`, and `validateConfig` bound to task 21's validator.
- [x] Declare the six commands with the exact action strings `runPds` accepts today (`keygen`, `login`, `init`, `sync`, `secret status`, `secret delete`), each with a non-empty `summary` and a `run(ctx, args)` that calls the matching function in `packages/pds/src/commands.ts` - signatures there stay as they are.
- [x] Parse each command's own flags inside its `run` from the `args` the SPI hands it - `--identifier <handle-or-did>` for `login`, `--yes` for `secret delete` - never reading `process.argv`, and pass the parsed values through in the shapes `login`/`secretDelete` already expect.
- [x] Declare `nodes(ctx)` on the plugin, returning `buildPdsNodes(ctx)` from task 23's `packages/pds/src/nodes.ts` - the member that makes pds the SPI's second consumer of the node contributor rather than only of commands. `nodes` takes the full `PluginContext<PdsConfig>` the lifecycle verbs build, not the narrowed `PdsContext` the commands take, because only the engine path has a boundary to construct one.
- [x] Default-export the plugin from `packages/pds/src/index.ts` while leaving the existing `export * from './commands.js'` and the type re-export untouched, so `syncAfterDeploy` and the five other functions stay importable by name.
- [x] Write `packages/pds/src/plugin.test.ts`: enumerate `plugin.commands` and assert the six actions with non-empty summaries; assert `validateConfig` rejects a bad block with task 21's message; assert each `run` reaches its function with the parsed arguments, covering both the success path and the refusal path for `secret delete` and `login`; assert `plugin.nodes(ctx)` returns exactly the one node `buildPdsNodes` produces, with the same id, and is the same array - no wrapper filtering or re-ordering it.
- [x] Confirm the plugin is inert: `blogwright pds <action>` still routes through `runPds`, and no CLI file changes in this task.
