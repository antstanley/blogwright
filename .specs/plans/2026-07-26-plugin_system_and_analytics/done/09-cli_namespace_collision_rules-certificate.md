## Residue

- **The dedupe drops the bundled half unconditionally, not only when the consumer half resolves.** `plugins.ts:185` filters a package out of the bundled candidates purely on its presence as a *name* in the consumer manifest, before any resolution is attempted. When a consuming repo **declares** a `blogwright-*` plugin that is not resolvable from `repoRoot` - a `pnpm install --prod` that pruned a devDependency, a hand-edited `package.json` before install, a pruned or never-installed `node_modules` under a globally installed CLI - while the CLI's own bundled copy **is** installed, the consumer candidate returns `{ found: false }` and `loadCandidate` classifies it `absent` (silently, by task 08's design), and the working bundled candidate is never probed. Verified against `dist/`: consumer and CLI manifests both listing `blogwright-pds`, only the CLI's copy installed › `plugins: []`, `failures: []`, one probe, from `/repo`. Against the parent commit the same fixture returns the plugin. §CLI → Plugin discovery is explicit that this outcome is the one the two-source union exists to prevent ("Any plugin that ships inside the CLI … would be invisible, and `blogwright pds sync` would stop working"), and it is silent - `blogwright plugin list` (task 17) would show neither the plugin nor a reason. Narrower than the defect it replaced (that one fired on a *correct* install; this needs an inconsistent one) and unreachable until task 26 gives `blogwright-pds` a `blogwright.plugin` field. One-line fix: dedupe after loading, on `LoadedPlugin.packageName`, keeping both candidates probed - or probe the bundled half only when the consumer half came back `absent`. No test pins the current behaviour either way.
- **Nothing mechanically enforces `known-commands.ts` staying a leaf.** The whole fix rests on that module having no imports; the constraint is stated forcefully in its comment (`:1-12`) but no lint rule, `knip` config or test would catch a future import being added, and the resulting `ReferenceError` reappears only once task 10's edge exists. A `no-restricted-imports` override scoped to that one file would make the property enforced rather than documented.
- **The task file is now stale.** Step 1 and the Pointers line still say `RESERVED_COMMANDS` is exported "from `packages/cli/src/cli.ts` beside `KNOWN_COMMANDS` (`packages/cli/src/cli.ts:66-75`)"; both registries now live in `known-commands.ts` and `cli.ts:66-75` is `HASH_COMMANDS` and the `TerminalFactory` doc. Task 10's pointer set, which the plan says adds `'plugin'` to `KNOWN_COMMANDS`, should be re-aimed at the new file before that task starts.
- **`KNOWN_COMMANDS` is now an exported mutable `Set`**, where it was module-private before; only `RESERVED_COMMANDS` carries `ReadonlySet<string>`. Not exploitable - the package's `exports` map publishes only `./rkey`, so no plugin can reach it - and nothing in the tree mutates it, but the asymmetry is free to remove.
