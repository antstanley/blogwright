## Residue

Notes for the validator: the change spec does not fix the wire type of `timestamp(ms)` (string of milliseconds versus number); the obligations require only that the derivation is total over the fixtures and reads no clock, so either input handling is acceptable provided a non-parsing value drops. `query` and `referrer` being empty strings rather than absent is not covered by the DoD - CloudFront emits `-` for absent values, and whether that becomes an empty string or a drop is left to the author. The `day` value's textual format (`YYYY-MM-DD` per the spec's `format: date`) is asserted only through the boundary fixtures' expected literals.

**Validator addenda (2026-08-30).** The three semantic decisions the residue left open are all settled defensibly and all documented at the point of decision:

- **`-`, `''` and whitespace mean absent** (`map-record.ts:161`): nullable column omitted, required column dropped. This matches `schema.ts`'s own statement that "CloudFront itself writes `-` for several of these when a request has nothing to say", and the residue explicitly delegates the choice. Confirmed against the change spec's §Record transformation, which specifies only step 5 ("drops records the schema cannot accept") and does not constrain this.
- **A number in a string column is rendered, not rejected** (`:150-155`): `asn: 64512` → `'64512'`. Any other non-string type (object, array, boolean) drops, "because there is no rendering of it that is not a guess". Sound: `String(64512)` is the same value in the type the column stores, whereas `String({})` is not.
- **`event_time` must render a four-digit year** (`:100-107`, `:192-195`). The reasoning is correct and the boundaries were re-derived independently: `9999-12-31T23:59:59.999Z` maps; one millisecond later `toISOString` switches to the expanded-year form `+010000-01-01T…`, whose first ten characters are `+010000-0` - not a date - and the regex drops it; `8_640_000_000_000_001` exceeds the representable `Date` range and drops on the `getTime()` NaN guard. The symmetric lower boundary also holds: year `0000-01-01` maps and one millisecond earlier drops.
- **The `int`/`long` columns accept non-integral values.** `NUMERIC_COLUMNS` distinguishes numeric from textual but not integral from fractional, so `sc-status: '200.5'` writes `200.5` into an Iceberg `int` column and `sc-bytes: '1.5'` writes `1.5` into a `long` (validator probe against `dist/`). Likewise `Number('0x10')` yields `16`. Not reachable from real CloudFront data - `sc-status` and `sc-bytes` are integer-valued fields - and outside the DoD, which asks only that the three columns be numbers and that a non-numeric value drop. Recorded as a follow-up for task 42's envelope or a later hardening pass, not as a gap in this task.
- **The row's value types are test-enforced, not type-enforced.** `map-record.ts:253` returns `columns as PageView`, an unchecked assertion, so a future 1:1-mapped **boolean** column would be routed to `stringFrom` and written as a string with no compile error. Verified by probe: adding such a column and its `FIELD_TO_COLUMN` entry **typechecks clean** but fails three `map-record` tests, including `writes only page_views columns, each in the JavaScript type its Iceberg type stores`. So the failure mode is a loud test failure, not an unmatched Firehose column - which is the property that matters - but the guard is the test, not the compiler.
- **Two comment defects, neither behavioural.** (1) `map-record.ts:104-106` claims "a `timestamp(ms)` in the wrong unit would partition the table under `+275760-0` rather than failing. This is the check that notices." Verified true for microseconds (drops, "falls outside the years 0000-9999") and nanoseconds (drops, "not a representable instant"), but **false for seconds**: `1788099825` maps silently to `1970-01-21T16:41:39.825Z` under day `1970-01-21`. The behaviour is defensible - CloudFront's field is milliseconds by definition - but the comment overstates the guard. (2) `schema.test.ts:99` still reads "which is deliberately unexported", which this task made false; see the judgement below.
- **A drop reason wording nit.** A required column whose field holds `-` reports `CloudFront field "x-host-header" is absent`, though the field was present. Operator-facing text; the field and column names are correct.

**On the stale comment left in `schema.test.ts:99`.** The implementer disclosed it deliberately, to keep "task 39's tests pass unmodified" literally true. The tradeoff is real but I would have made the one-clause edit. Three reasons: the claim that actually matters is "task 39's tests still pass and no expected value moved", which a comment edit does not weaken and which a diff proves directly (this validator proved it by sha256 and by reading the full `schema.ts` diff); the comment's own load-bearing half - "comparing the constant against the list it is spliced into would hold no matter what the constant said" - is *more* important now that the constant is importable, so the paragraph deserved a touch anyway; and the file now contradicts `schema.ts:120` ("Exported for its one consumer") from within the same task's blast radius, which is the kind of drift that teaches the next reader to distrust the rest of a file whose whole purpose is to be trusted about constants.
