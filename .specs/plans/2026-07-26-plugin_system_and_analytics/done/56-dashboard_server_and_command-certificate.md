## Residue

- **No DuckDB starts in this task's tests.** `commands.test.ts` constructs the real `createDuckDbAnalyticsQuery` but never requests `/api/queries/…`; the adapter opens its session lazily (`session ??= openSession()`, reached only from `run`), so construction touches neither the network nor the native library. Six tests, 27 ms, offline, deterministic. Task 46's `adapters/duckdb-query.test.ts` does start a real in-memory DuckDB, by design and disclosed.
- **Gap 1 - "the adapter is constructed only here" rests on a grep and a read.** Accepted. The claim is a *static* property of the module graph, and a grep is the correct instrument for a static property; the DoD itself names the grep as the evidence. Manufacturing a runtime assertion would require either starting DuckDB (forbidden by the package's own test rule) or injecting a construction seam that exists only for the test - which would weaken the very property being asserted, since the seam is another construction site. Declining to fabricate the assertion was the right call.
- **Gap 2 - grep artefacts.** Both confirmed and reproduced above (O4 and O6). `grep -rnF` narrows the `0.0.0.0` noise to prose plus one pre-existing user-agent fixture.
- **Gap 3 - suite hygiene.** Confirmed; the `Reviewable:` filter `vitest run server` matches 37 tests and does **not** match `commands.test.ts`, which is why it was run separately (43 together).
- **Static import of the adapter** rather than a dynamic seam. Measured here: importing `dist/adapters/duckdb-query.js` cold takes **38 ms** (the implementer's ~25 ms is a warm figure and is the right order). Loading the module loads the native addon but opens no database. Judged acceptable - a dynamic seam would add an untestable branch to buy tens of milliseconds on a command whose next act is a network round-trip to S3.
- **Non-blocking observations, none of which violates the contract, the change spec, or the DoD:**
  1. `HEAD` is answered 405. RFC 9110 §9.1 says a server MUST support GET and HEAD. No practical impact for a prebuilt SvelteKit app in a browser (navigation and subresource loads are GET), but `curl -I` and naive uptime probes will see 405. If the method guard is ever relaxed, `HEAD` must not become a path that reads a body.
  2. No `Host` header validation and no CORS headers, so the classic loopback-dashboard DNS-rebinding shape is not closed: a page the operator visits while the dashboard is running could, with attacker-controlled DNS, read the named-query JSON as same-origin. Impact is bounded to the operator's own traffic figures - no SQL, no writes, no file reads outside `appDir`, no credential exposure - and a plain cross-origin `fetch` is already blocked from reading the response by the absent `Access-Control-Allow-Origin`. Outside every obligation in this task and unmentioned in the change spec; recorded so task 57 (which builds the app) can close it with a `Host` allow-list if wanted. `X-Content-Type-Options: nosniff` is likewise absent.
  3. `GET /nested` (no trailing slash) is a 404 rather than a redirect to `/nested/`; only the trailing-slash form is tested.
  4. The `Object.hasOwn` on `INCLUDE_BOTS_VALUES` is the one guard in the diff with no test under it (see the survivor list).
- **Occupied port and process-level signals.** Both are outside the obligations but both are covered anyway (`fails with an actionable message when the port is already held`, in both files; `leaves no signal listener behind once it has stopped`). The `SIGINT`/`SIGTERM` registration is a direct `process` API in the composition root, which is where the repo puts such things; the DoD's port rule addresses domain modules and is not engaged.
- **`close()` destroys connections.** Reproduced exactly as reported: removing `server.closeAllConnections()` is killed by **one** test only - `closes while a query is still running` - because Node ≥ 19 already closes *idle* connections, so the plain rebind-after-close test survives it. The deterministic in-flight test (a port that never answers, waited on with `waitFor` until the fake records the call, then `close()`) is what makes that line falsifiable, and without it the sweep would have scored a genuine defect as SURVIVED.
