## Residue

Notes for the validator, not obligations: the boundary day (the day the Firehose delivery was created) is deliberately never backfilled - up to one day of history is lost at the seam, a stated precision limit; do not treat a gap on that day as a defect. Whether DuckDB's Iceberg write support (documented as preview) holds for the S3 Tables attach in write mode is the same vendor risk the spec's Assumptions record for reads, and the `AnalyticsIngest` port is what contains it - if the write syntax moves, the adapter moves and the domain does not. CloudWatch's `FilterLogEvents` pagination on large days is bounded by the site's blog-scale volumes; a pathological day that exhausts memory is out of scope here and worth a follow-up limit if observed.

**Validator's residue - two non-blocking findings, neither a defect in shipped behaviour.**

1. *An unasserted idempotency property.* `rowsAlreadyIn` binds `includeBots: true` so a day holding only bot traffic counts as occupied. Mutating it to `false` **survives the entire 793-test analytics suite**. The shipped value is right and the doc comment explains why, but nothing would catch a later edit; with `false`, a bot-only day would be re-inserted on every run, which is the one duplication the whole design exists to prevent. One assertion on `countingQuery`'s received params would close it.

2. *The spec assumes a field set nobody verified, and the assumption is load-bearing for this command in production.* Confirmed against the code, not inferred: `packages/cli/src/nodes.ts:785` calls `createDelivery(source, destArn)` with **no** `recordFields`, so the site's CloudWatch delivery carries AWS's default CloudFront field set, while `packages/analytics/src/nodes.ts:2909` selects `CLOUDFRONT_RECORD_FIELDS`. The two sets can therefore differ, and `mapRecord` drops any record missing `timestamp(ms)`, so a divergence drops every backfilled record on a required column. This is *the spec assuming something unverified*, not *the code being wrong*: the command does exactly what §Backfill specifies, narrowing the site's delivery is explicitly out of that spec's scope, the action is optional, hand-run and inserts nothing on failure, and the mitigation is loud and diagnostic - drops are counted per day and the first reason names the column and the CloudFront field behind it. It does not block. The one improvement worth a follow-up is that the closing `ok` summary reads "inserted 0 rows across 0 days" at the same level whether the log group was empty or every record dropped.
