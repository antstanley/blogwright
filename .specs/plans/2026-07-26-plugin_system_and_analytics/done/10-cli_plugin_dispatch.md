## Steps

- [ ] Create `packages/cli/src/plugin-commands.ts` and `packages/cli/src/plugin-commands.test.ts` here - this task is their sole author. Tasks 13, 16 and 17 all add actions to the same table and each says "write" the test file; on the stated graph none depends on the others, so without a named owner three tasks race to create the same two files. Open the module with a comment saying so.
- [ ] Add `plugin` to `KNOWN_COMMANDS` (`packages/cli/src/known-commands.ts`, moved there by task 09) and replace the unknown-command error at `:117-121` with a fall-through to a new `runPlugin` helper, so a first positional that is neither a built-in nor `plugin` reaches plugin dispatch instead of failing.
- [ ] In `runPlugin`, resolve the repo root through `ports.fs` and call `discover(repoRoot, cliPackageDir(), ports)` - three arguments, the middle one task 08's composition-root helper, because a consuming repo depends on `blogwright` and never on `blogwright-pds`, so a call that omits it discovers no bundled plugin at all. Then build the context through the injected factory from task 07 and adapt it in a named function - `toPluginContext(ops, plugin, …)` - rather than assigning it. An `OpsContext` is NOT assignable to a `PluginContext`: it carries thirteen of the sixteen members and none of `pluginConfig`, `siteState` or `record`, so a bare assignment is `TS2739`. The adaptation supplies those three and nothing else, with no cast and no `any` anywhere in it: `siteState` is the `OpsContext`'s already-loaded `state` passed through as the read-only view, `record(nodeId, outputs)` writes into `state.resources`, and `pluginConfig` is `{}` until task 19 fills it from the plugin's validator. Task 16 re-points `store`, `state` AND `save()` at the plugin's scoped store - `save()` included, because the `OpsContext`'s closes over the site's store and the site's state object (`packages/cli/src/context.ts:153-155`) and typechecks straight through, so it is the one member the compiler will not catch. Until task 16, all three state surfaces read and write the site's store, which is why nothing between this task and task 16 may call `plugin.nodes`.
- [ ] Match the longest declared `action` against the leading positionals so multi-word actions such as `secret status` dispatch by declaration rather than the hand-rolled shifting at `packages/cli/src/cli.ts:195`, and pass the remaining positionals together with the parsed flag values to `run(ctx, args)`.
- [ ] Resolve the environment BEFORE building the context: the first unconsumed positional after the matched action is the environment, `--env` overrides it, and the default stays `production`. This is what `runPds` does by hand at `packages/cli/src/cli.ts:196` (`positionals[secret ? 3 : 2]`), and preserving it is what keeps `blogwright pds sync staging` and `blogwright pds secret status staging` working after task 29 deletes that code. Silently defaulting to `production` is the single most likely way this plan breaks the migration spec's no-user-visible-change promise, so the environment must be resolved by the dispatcher, not left to each plugin.
- [ ] Map the plugin command's return value to `main`'s exit code, so a command that reports failure exits non-zero without throwing.
- [ ] Report an unknown plugin name with a message stating that no built-in command or installed plugin claims it and suggesting `blogwright plugin list`, and an unknown action with the known plugin's declared actions listed - both returning exit code 1.
- [ ] Extend `packages/cli/src/cli.test.ts` with dispatch tests over fake plugins served by the map-backed `ModuleLoader`: a multi-word action, a flag-carrying invocation whose value is asserted at `run`, an unknown plugin, an unknown action, exit-code mapping, a laziness test running `deploy`, `status` and `bootstrap` that asserts the loader fake was never called, and four environment cases - single-word action with and without a trailing environment, multi-word action with a trailing environment, and `--env` overriding a positional - each asserting the environment the context factory was called with; add a changeset for the new dispatch surface.

## Definition of done

- [ ] A first positional that is neither a built-in nor `plugin` triggers discovery and dispatches to the matching plugin command with the remaining args, multi-word actions included and tested - this is not optional, because task 29 requires `pds secret status` and `pds secret delete` to be declared by the plugin rather than positionally shifted by hand - and a plugin command's return value maps to the process exit code.
- [ ] Flag values reach the command: a test asserts a flag-carrying invocation (the `--identifier` and `--yes` shapes task 29 depends on) arrives at `run()` with its value, not merely that a missing-flag refusal fires, because a refusal message looks like correct behaviour and would hide a wiring bug.
- [ ] An unknown plugin name reports that no built-in command or installed plugin claims it, suggests `blogwright plugin list`, and exits 1 (test on both message and code); an unknown action inside a known plugin lists that plugin's actions and exits 1 (test).
- [ ] `discover` is called with all three arguments, the CLI package directory coming from task 08's `cliPackageDir()` rather than being re-derived here - a test asserts a plugin bundled with the CLI dispatches from a consumer `package.json` whose only dependency is `blogwright`, which is the case task 29 makes load-bearing.
- [ ] Discovery is lazy - a test running `deploy`, `status` and `bootstrap` asserts the `ModuleLoader` fake was never called - and the context handed to `run` is built by the named `toPluginContext` adaptation with no cast and no `any`, `grep -n "as PluginContext" packages/cli/src/plugin-commands.ts` returning nothing; a changeset records the new user-facing dispatch surface.
- [ ] Meets the repo definition of done (see plan.md baseline).
- [ ] Reviewable: run `pnpm --filter blogwright exec vitest run cli --reporter=verbose`; confirm a fake plugin declaring `secret status` is reached by `blogwright fake secret status --yes` with `yes` true at `run()`, and that the laziness test fails when the `discover` call is hoisted above the built-in switch.
