## Steps

- [x] Write `packages/analytics/src/plugin.ts` declaring the `Plugin` object: `name: 'analytics'`, a one-line `description` in the voice of the `pds` USAGE block at `packages/cli/src/cli.ts:33-47`, `configKey: 'analytics'`, and `validateConfig` bound to task 44's `validateAnalyticsConfig` rather than a second validator written here.
- [x] Read task 16's precedence decision out of `packages/cli/src/plugin-commands.ts`'s module comment before writing the table, and declare exactly `status`, `dashboard` and `backfill` (the optional one-shot action the spec's §Namespace and commands declares; declaring it is legal because only `bootstrap` and `destroy` are reserved to the generic verbs) - never `bootstrap` or `destroy` (a plugin may not import the CLI and so cannot run `applyGraph`/`destroyGraph` itself), and **never `init`**. A plugin's declared commands take precedence over the generic actions, so declaring an `init` command here would shadow the generic action that renders and splices the config block: `blogwright analytics init` would ask the operator every question and then write nothing. `init` is supplied ONLY as the `Plugin.init(io)` contributor below. (pds is the opposite case - it declares a real `init` command that creates the publication record and writes no config block at all, which precedence permits: a declared `init` owns the action, not an obligation to write config.)
- [x] Give every declared action a `summary` fit for one `blogwright --help` line, and state `--yes` in the summary of any destructive action the precedence decision left to the plugin.
- [x] Point the `status`, `dashboard` and `backfill` entries at named functions in `packages/analytics/src/commands.ts` whose bodies tasks 55, 56 and 61 fill in - each raising an error naming its task until then - so the table is written once here and no later task edits it.
- [x] Write the `init` contributor over task 03's `PluginInitIo`: ask only the questions task 44's config carries defaults for, default each prompt from those constants, and return `ConfigBlockEntry[]` in the shape `renderConfig` builds at `packages/cli/src/init.ts:48-65` - returning an empty array when the operator declines and never touching `ctx.ports.fs`.
- [x] Default-export the plugin from `packages/analytics/src/index.ts` beside the package's existing named exports, and add `"blogwright": { "plugin": "analytics" }` to `packages/analytics/package.json`, changing no other field and adding no dependency or devDependency on `blogwright`.
- [x] Write `packages/analytics/src/plugin.test.ts`: load the package the way CLI discovery does (read the manifest field from `package.json`, take the module's `default`) and pass it through core's `validatePlugin(module, 'blogwright-analytics')`; assert the declared action set and that it intersects the CLI's reserved verbs nowhere; drive `init` twice through `createScriptedTerminal` - an all-defaults answer set and a customised one - asserting the returned entries and that no write reached the in-memory `FileSystem`.
