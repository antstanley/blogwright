## Steps

- [x] Decide the precedence and write it into the module comment of `packages/cli/src/plugin-commands.ts`: `bootstrap` and `destroy` are always the generic verbs, because a plugin may not import the CLI and therefore cannot run the engine itself, so a plugin declaring either is rejected with an error naming the plugin and the colliding action; `status` is the generic verb unless the plugin declares one, because `read()` lives on the plugin's own nodes.
- [x] Add the rejection to the declared-action collision check task 13 already extended - task 09's collision pass in `packages/cli/src/plugins.ts`, the home task 13 decided and recorded - so a bad plugin fails at load with the collision named, not mid-command, and both rules live in one module rather than one here and one in core.
- [x] Build the plugin's context in `plugin-commands.ts` from the `OpsContext` `createContext` returns, populating BOTH state surfaces from different stores: `siteState` is the unscoped store's already-loaded `state` (the site's `state/<env>.json`, passed through read-only and never written), while `store` becomes a `StateStore` scoped to the plugin's `name`, `state` becomes that scoped store's own `load()` - an `OpsState`, not a bare outputs map, because `destroyGraph` does `delete ctx.state.resources[node.id]` (`packages/cli/src/graph.ts:94`) - and `record()` writes into `state.resources`. Every other field - clients, ports, names, tags, logger - passes through as-is, and `save()` re-points at the scoped store. Do not overwrite `siteState` with the scoped load; task 53's log-delivery node reads the site's distribution outputs through it and cannot find them in `state/<env>.analytics.json`.
- [x] Implement the three verbs over `plugin.nodes(ctx)`: `bootstrap` calls `applyGraph`, `destroy` refuses without `--yes` with the same message shape as `commands.ts:56` then calls `destroyGraph` followed by the scoped `store.delete()`, and `status` calls task 15's extracted read loop and renders through the same interactive/plain branch.
- [x] Gate all three on `plugin.nodes` being declared: a plugin without it does not gain the verbs, and asking for one lists the plugin's real actions and exits non-zero.
- [x] Guard the site's own `destroy` (`packages/cli/src/commands.ts:54`): before `destroyGraph(buildNodes(ctx), ctx)` at `:62`, list the bucket's `state/` prefix through `ctx.clients.s3.listObjects` and refuse when any object matches `state/<env>.<scope>.json`, naming each scope and its `blogwright <scope> destroy <env> --yes` - the remedy MUST carry the environment (CORRECTED 2026-08-30; the original text here said `blogwright <scope> destroy --yes`, and prescribing that env-less form is what put the defect in the code). `runPlugin` resolves the env as `values.env ?? envPositional ?? DEFAULT_ENV` with `DEFAULT_ENV = 'production'`, while `runPreview` always builds `env: 'preview'` - so on `preview teardown` the env-less remedy is ALWAYS wrong, and it points at production: best case it loads empty state and removes nothing, leaving the operator stuck in the same refusal; worst case it tears down the live production analytics stack from a preview teardown. Scoping changes the key, not the bucket, and `bucketNode.delete()` empties every prefix (`packages/cli/src/nodes.ts:66`) - without the guard a site teardown deletes the plugin's record while its resources live on, and the plugin's own `destroy` then loads empty state, reads `false` from every node and removes nothing. The guard reads the bucket, not the plugin registry, so it holds even for a plugin that has since been uninstalled.
- [x] Keep the guard cheap and non-lazy-breaking: it is one `listObjects` on a prefix the command is about to delete anyway, and it runs inside `destroy` - not in `createContext` - so no other command pays for it and discovery stays lazy.
- [x] Write `packages/cli/src/plugin-commands.test.ts` cases with a fake node-contributing plugin and a recording S3 client, asserting the state keys touched by a plugin bootstrap and, separately, by `blogwright bootstrap` and `blogwright destroy` with that plugin installed.
- [x] Cover the guard in both directions: `blogwright destroy --yes` with `state/<env>.analytics.json` present refuses, names `blogwright analytics destroy <env> --yes` with the environment interpolated (CORRECTED 2026-08-30 - see the step above; an env-less remedy points at production and is ALWAYS wrong on `preview teardown`), and issues no delete at all (asserted on the recording S3 client, not on the message alone); with no scoped object present it proceeds exactly as today, byte-identical in the calls it makes.
- [x] Write the changeset recording the three new user-facing verbs and the precedence rule.
