## Steps

- [x] Declare `AnalyticsQuery` in `packages/analytics/src/ports.ts` as `run(name, params)` returning rows in domain vocabulary - the operations the dashboard and `analytics status` need, not a re-export of DuckDB's surface - with a doc comment stating that the vendor library lives only behind it.
- [x] Declare the query parameter type carrying the date range and the bot-inclusion flag, whose default is read from `config.analytics.bots` (task 44) rather than restated.
- [x] Declare the named set in `packages/analytics/src/queries.ts` as one keyed table - views over time, top paths, referrers, countries, status codes, cache hit ratio, and unique visitors by `visitor_key` - each definition carrying its SQL text with bind placeholders and the parameter names it binds. The unique-visitors definition computes daily uniques and reports a range total as their sum - never a `COUNT(DISTINCT …)` spanning days, which the daily salt rotation makes uncomputable (the spec's Decision *Daily salt rotation stands*, settled 2026-07-27) - and its result rows are labelled as summed daily uniques so the dashboard cannot present them as a cross-day distinct count.
- [x] Write the lookup that resolves a name to its definition and raises an error listing the available names when the name is unknown, and validate the date range at the same boundary - an absent or inverted range raises rather than silently defaulting.
- [x] Write the fixture-backed fake `AnalyticsQuery` beside the port so every consumer's test substitutes at the port, and no test in the package starts DuckDB.
- [x] Write `packages/analytics/src/queries.test.ts` iterating the whole named set to assert each definition's SQL text contains no interpolated caller value and binds its parameters, plus the unknown-name and bad-range rejection cases.
