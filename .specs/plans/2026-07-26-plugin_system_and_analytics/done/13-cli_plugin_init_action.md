# Task 13 - Add the generic `blogwright <plugin> init` action

**Plan:** [plan.md](../plan.md) · **Certificate:** [13-cli_plugin_init_action-certificate.md](13-cli_plugin_init_action-certificate.md)

**Implements:** [2026-07-26-cli_plugin_system.md §CLI → `blogwright <plugin> init` (Add)](../../../changes/2026-07-26-cli_plugin_system.md) ("`blogwright <plugin> init` on a repo with an existing config asks that one plugin's questions and inserts its block into the existing file") and §Plugin SPI → The `Plugin` contract (the `init?(io)` contributor)
**Depends on:** 03, 10, 12
**Produces:** `blogwright <plugin> init` on a repo with an existing config runs the plugin's `init(io)` against the Terminal port and splices the returned block into the file the environment resolves to, with a plugin-declared `init` command taking precedence over the generic action
**Pointers:** `packages/cli/src/plugin-commands.ts` (from task 10 - the generic actions live beside dispatch), `packages/cli/src/init.ts:23` (`ask` - the prompt/validate/retry loop over `Terminal.question` the `io` reuses; currently module-private), `packages/cli/src/context.ts:85-102` (`loadConfig` - the candidate list `config/<env>.jsonc`, `ops.config.jsonc`, or `--config`; the action must target exactly the file this resolves), `packages/cli/src/config-block.ts` (task 12 - `renderConfigBlock` and `spliceConfigBlock`), `packages/cli/src/cli.ts:107` (the built-in `init` branch, which this action does not change)

## Steps

- [ ] Extract the candidate resolution at `packages/cli/src/context.ts:86-91` into a named `resolveConfigPath(fs, source)` returning the path of the first candidate that exists, and have `loadConfig` call it, so the init action writes to exactly the file `loadConfig` would read rather than re-deriving it.
- [ ] Build the `io` handed to `init` in `plugin-commands.ts` over `ctx.ports.terminal`, reusing the retry/validate loop at `init.ts:23-40` (export it, or lift it into a shared prompt module) so no plugin ever writes its own prompt code.
- [ ] Add the generic `init` action to the plugin dispatch table from task 10, resolved *after* the plugin's own `commands`, so a plugin declaring an `init` command wins - record the precedence rule in the module comment, naming pds as the reason (its `init` creates the publication record and must not be replaced by a config writer). Precedence is the whole rule for what a declared `init` may do: it owns the action, and whether it writes a config block is its business, not the SPI's.
- [ ] Add the one part of that rule a boundary check can decide, and DECIDE ITS HOME here rather than leaving it open: it joins task 09's collision pass in `packages/cli/src/plugins.ts`, not core's `validatePlugin`. This task runs before task 16, which adds the sibling `bootstrap`/`destroy` rejection to the same place, so leaving the choice to whichever executed first is how two checks end up in two modules. The collision pass is the right home because the rule is about actions the *CLI* contributes generically - core declares the `Plugin` contract and must not know that a host somewhere offers an `init` action - and because `plugins.ts` already holds `RESERVED_COMMANDS` and reports collisions as load failures rather than throwing. (Task 09's pass is in place by here through task 10, which depends on it.) The rule itself: a plugin declaring BOTH an `init` command and an `init?(io)` contributor is rejected at discovery, naming the plugin. That combination is unsatisfiable rather than merely odd - precedence gives the command the action, so the contributor's questions would be asked nowhere. Declaring either alone is valid: pds declares the command and no contributor, analytics the contributor and no command.
- [ ] Render the returned block with `renderConfigBlock` and insert it with `spliceConfigBlock`, writing through `ctx.ports.fs.writeText` only after the splice returns; let the splice's own errors propagate to the CLI's exit-code path unchanged.
- [ ] Handle the two empty cases explicitly: a plugin with neither a declared `init` command nor an `init` contributor reports the action is unavailable and lists the actions it does have; a contributor returning no block writes nothing and says so.
- [ ] Write `packages/cli/src/plugin-commands.test.ts` cases for all of the above using fake plugins, `createMemoryFileSystem` and `createScriptedTerminal`, asserting on written file contents and on the fact that nothing was written where nothing should be.

## Definition of done

- [ ] `blogwright <plugin> init` on a repo with an existing config calls the plugin's `init(io)`, renders the returned block, splices it into the file the environment resolves to (`config/<env>.jsonc`, `ops.config.jsonc`, or `--config`), and the written file re-read through `parseConfig` succeeds - verified end to end against the in-memory `FileSystem` and a scripted `Terminal`, so the wizard can never leave an unloadable file behind.
- [ ] The `io` handed to `init` prompts through the `Terminal` port and no plugin path reaches `node:readline`, enforced by `pnpm lint`'s `no-restricted-imports` rule (`.oxlintrc.json` - `plugin-commands.ts` is not in the override list).
- [ ] A plugin that declares its own `init` command wins over the generic action - required by the pds migration, whose `init` creates the publication record and writes no config block at all - with one test for a plugin declaring an `init` command and one for a plugin carrying only an `init` contributor. A plugin declaring both is rejected at discovery naming the plugin, with a negative-space test, and the rejection lives in task 09's collision pass in `packages/cli/src/plugins.ts` - the decided home task 16 then extends with `bootstrap`/`destroy`, so the declared-action collision rules grep to one module; nothing requires a declared `init` command to write a config block, and no test asserts that it does.
- [ ] The refusal and empty paths behave: a plugin with neither reports the action is unavailable, lists the actions it does have and exits non-zero; a config already containing the plugin's key exits non-zero with the splice module's message and the file is left byte-identical (the test asserts the file was not written); a contributor that yields no block writes nothing and says so - one test each.
- [ ] Meets the repo definition of done (see plan.md baseline).
- [ ] Reviewable: run `pnpm --filter blogwright exec vitest run plugin-commands --reporter=verbose`; confirm a fake plugin declaring `init` reaches its own `run` and never the config writer, and that the already-configured case leaves the in-memory file's contents identical to what the test seeded.
