## Residue

Notes for the record, not obligations.

1. **`createContext`'s own two lines have no runtime test - confirmed live, and it is the one place a silent regression could hide.** Mutating `packages/cli/src/context.ts:211` to `configDocument: {}` passes `pnpm typecheck` AND the entire repo suite (core 149, build-agent 27, pds 117, analytics 306, cli 327 - all green). In production that mutation would make every plugin see an ABSENT block regardless of what the operator wrote: `blogwright analytics …` with `"analytics": {"namespace": "marketing"}` would silently run on `namespace: "web"`. Judged **not owed by this task**: `createContext` is the composition root, has never had a direct test, constructs real AWS clients via `createClients` and calls `sts.getAccountId()` with no transport seam on `ContextOptions` - adding one is a design change, not a test fix. The obligation is discharged by `pnpm typecheck` (the field's presence and type), by the dispatch fixtures' `makeContext` reproducing those exact two lines over the REAL `loadConfig`, and by every other link in the thread being independently pinned by a mutation. Recorded here so that whoever adds a `clients` seam to `ContextOptions` knows this assertion is the first one to write.
2. `resolvePluginConfig`'s `typeof plugin.validateConfig !== 'function'` probe is defensive and unpinned: weakening it to `=== undefined` leaves all 327 CLI tests green. `validatePlugin` (`packages/core/src/plugin.ts:385+`) type-checks neither `configKey` nor `validateConfig`, and the module comment states this is the same probe `plugin-commands.ts` uses for the `init` contributor - house style, and the DoD requires no test for it.
3. A plugin declaring `configKey` but NO `validateConfig` gets `{}` on `pluginConfig` - the same placeholder shape the correction removed. Harmless today (`Plugin<TConfig>` cannot produce a `TConfig` without a validator, so such a plugin cannot read it as anything) and outside the DoD, but it is the one surviving path where an unvalidated `{}` reaches a plugin.
4. `pluginBlock` is `raw[key]`, an ordinary property read on a `JSON.parse` result, so a plugin declaring `configKey: 'constructor'` (or any `Object.prototype` name) would receive an inherited value rather than `undefined`. `pluginBlock` is task 03's, `configKey` is unconstrained by `validatePlugin`, and no real plugin declares a key yet - noted, not charged here.
5. `(err as Error).message` in the re-raise yields `undefined` for a validator that throws a non-`Error`. Consistent with `cli.ts:353` and with the SPI's "raises in the repo's own error vocabulary"; not a defect.
6. The scope choice task 28 must reason about is at `packages/cli/src/plugins.ts:74-96`, stated as a `DECISION` block with both reasons spelled out - its wording is adequate for that purpose.
7. **This certificate's authored O2 encoded the PRE-correction contract** and was superseded per P4. Task 44's gate is what proved the original text broken; the correction was verified load-bearing here by mutation M7 (restoring it reddens a named test) and by end-to-end execution against the built `dist`.
