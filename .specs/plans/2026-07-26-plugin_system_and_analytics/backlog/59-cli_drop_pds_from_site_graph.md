## Steps

- [ ] Delete the `if (ctx.config.pds)` statement block at `packages/cli/src/nodes.ts:913-927` - including task 27's inline `<siteName>/atproto` default, which exists only to keep that block's ARN total and dies with it - and correct the doc comment at `:823` so it no longer claims the role grants access to the PDS secret.
- [ ] Run `pnpm knip` and clear anything the removal orphans. `nodes.ts` imports nothing from `blogwright-pds` before this task and must import nothing after: the grant moved by way of the plugin contributing its own node (task 23), not by the CLI reaching into the plugin, so there is no import to delete here - confirm that with `grep -c blogwright-pds packages/cli/src/nodes.ts` returning `0`.
- [ ] Move the ARN assertions out of `packages/cli/src/nodes.test.ts:194-208` - task 23 already reproduces the policy document against the plugin's node, and task 27's `undefined` guard has nothing left to guard - so delete both here rather than duplicating coverage, and add their negative: a context WITH `config.pds` set produces an OIDC policy containing no `secretsmanager` statement at all.
- [ ] Write the changeset and the upgrade note, and state the mechanism correctly. The old grant is a **statement inside** the `<env>-deploy` inline policy, not a separate policy: `applyOidcRole` replaces that whole document on every `blogwright bootstrap` (`packages/cli/src/nodes.ts:840-842,962`), so it does not survive until the operator acts - it survives until their next site bootstrap. The note therefore reads: run `blogwright pds bootstrap` once before your next `blogwright bootstrap`; a stack that skips it loses the grant at that point, the post-deploy sync warns without failing the deploy, and `blogwright pds bootstrap` heals it.
- [ ] Do NOT execute the pds spec's §Merge plan steps 4–5, and record why: this task lands §The site graph drops its pds branch, but §`bootstrap` warns while plugin state exists is still outstanding and lands at task 60 - a spec is not merged while one of its `Proposed changes` blocks is, the same rule that already split tasks 20/58 for the plugin-system spec and, for this one, defers the flip past task 30 and past this task to task 60. Write the deferral into the change description naming task 60 as the flip's owner, and leave the spec's entry in `.specs/README.md`'s pending list.
