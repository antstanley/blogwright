## Steps

- [ ] Give the guards something to discriminate on before writing them: widen `deliveriesForSource` (`packages/core/src/aws/logs.ts:139-153`) from `Promise<string[]>` to a list of `{ id, deliveryDestinationArn }`: add the field to the response type at `:144` — `DescribeDeliveries` already returns it beside `id` — and carry it through the filter at `:147-149`, which today keeps `d.id` alone. Neither existing lookup can express "the site's own delivery" — `findDeliveryIdBySource` returns a single id chosen by `.find()` and `deliveriesForSource` drops everything but `d.id` — and DEVELOPMENT.md §Where validation lives forbids the workaround, because the CLI never issues a raw AWS call. The widening lands here rather than in task 37 because the retry loop at `packages/cli/src/nodes.ts:753-757` is its only caller and this task rewrites it; update the two-line fake at `packages/cli/src/nodes.test.ts:63` to the new shape in the same change. Leave `findDeliveryIdBySource` untouched — `delete()` stops using it.
- [ ] In `delete()`, read `deliveriesForSource` first. Delete the site's own delivery and destination, then delete the delivery source ONLY when no other delivery remains; when others remain, leave the source in place and fail with a message naming them and pointing at `blogwright analytics destroy`. Today the source is deleted unconditionally, and with a second delivery attached AWS returns a Conflict that `deleteDeliverySource` does not catch — so `blogwright destroy` throws partway through teardown, after the distribution is already gone.
- [ ] In the `ConflictException` retry, delete only the site's own delivery id rather than iterating `deliveriesForSource` and deleting all of them. The current loop silently removes the analytics delivery while the plugin's scoped state still records it as `configured`, so `analytics status` reports healthy and CloudFront has stopped delivering — a silent data-loss path, which is the worst shape a bug can take here.
- [ ] Identify "the site's own delivery" as the entry whose `deliveryDestinationArn` names `ctx.names.deliveryDestination`, not by position and not from state. Match on the name the ARN carries in its final segment, in one named predicate both guards call: the recorded `destination` output (`packages/cli/src/nodes.ts:731`) is empty exactly when the retry needs it, because `putDeliverySource` throws the Conflict at `:721-726` before `putDeliveryDestination` ever runs. The name is deterministic for the environment, so it also matches the previous stack's delivery on a destroy → bootstrap cycle — which is the delivery the retry is there to remove. `findDeliveryIdBySource` uses `.find()` (`logs.ts:131`) and returns whichever delivery AWS lists first, which is not necessarily the site's once a second exists; the widened list, not that lookup, is what both guards read.
- [ ] Extend `packages/cli/src/nodes.test.ts` with the recording `logsUsEast1` fake, whose `deliveriesForSource` at `:63` now returns `{ id, deliveryDestinationArn }` entries: a `delete()` against a source carrying one foreign delivery leaves the source alive and raises with that delivery named; a `delete()` against a source carrying only the site's own removes all three in the documented order; a Conflict retry with a foreign delivery present deletes only the site's id and leaves the foreign one in the call log. Add the `LogsClient` half in `packages/core/src/aws/logs.test.ts`: a paginated `DescribeDeliveries` response maps to ids paired with their destination ARNs, and a delivery on another source is still filtered out.
- [ ] Write the changeset: `blogwright destroy` can now fail where it previously threw a Conflict, which is the point — it fails early with an actionable message instead of part-way through.

## Definition of done

- [ ] `deliveriesForSource` returns each delivery's id together with its `deliveryDestinationArn`, so "the site's own delivery" is expressible without a raw AWS call from the CLI; a `LogsClient` test asserts the mapped shape from a paginated `DescribeDeliveries` response, and `findDeliveryIdBySource` is unchanged.
- [ ] `delete()` never deletes a delivery source carrying a delivery it does not own; it fails with a message naming the foreign delivery and `blogwright analytics destroy`, asserted by test, and the source is still present in the fake's state afterwards.
- [ ] With no foreign delivery present, `delete()` still removes delivery → source → destination in the order the comment at `nodes.ts:763-768` documents, proved by an unchanged call-order assertion — this task must not regress the existing teardown.
