## Steps

- [ ] Declare `Plugin<TConfig = never>` generic over the config block it owns, with `validateConfig?(raw: unknown): TConfig` - it validates AND RETURNS the resolved, defaulted block. A validator that returns `void` has nowhere to put defaults, which is what breaks pds (task 22) and analytics (task 44). The default argument is `never`, not `unknown`, so a plugin owning no `configKey` writes bare `Plugin`; inside it `ctx.pluginConfig` is `never`, so every property read off it is `TS2339: Property '…' does not exist on type 'never'` (verified against this repo's tsc 6.0.3), which is what a mistaken read actually looks like. Record the one unsoundness in the doc comment rather than designing around it: `const n: number = ctx.pluginConfig` compiles, because `never` is assignable to everything - the check `never` buys is at the property, not the whole field, and `unknown` would trade that away for a narrowing the plugin has no schema for.
- [ ] Declare `PluginContext<TConfig>` carrying `pluginConfig: TConfig`, populated by the CLI at dispatch from `validateConfig`'s return. A plugin reads its own settings there, never from `ctx.config`: `OpsConfig` (`packages/core/src/config.ts:68`) has no index signature, so `ctx.config.analytics` is `TS2339: Property 'analytics' does not exist on type 'OpsConfig'` under this repo's strict settings, and the only escapes - a cast or `any` - are banned by DEVELOPMENT.md §Code style.
- [ ] Give the host a typed route to a plugin's raw block, because there is none today: `parseConfig` (`packages/core/src/config.ts:242-245`) discards the parsed document and returns `OpsConfig`, whose lack of an index signature makes `config[plugin.configKey]` a `TS7053`. Export `parseConfigDocument(text): { config: OpsConfig; raw: Readonly<Record<string, unknown>> }` from `packages/core/src/config.ts`, with `parseConfig` becoming its `config` half so no existing caller changes, and `pluginBlock(raw, key): unknown` reading the block out of that document. An index signature on `OpsConfig` would be the wrong fix - it would also silence typos on the known keys. The only consumer is the CLI's dispatch path (task 19), which hands the `unknown` straight to `validateConfig`; plugins never call it.
- [ ] Declare `PluginCommand` with `action: string`, `summary: string` and `run(ctx: PluginContext, args: string[]): Promise<void>`, documenting that `action` may contain spaces so `secret status` (`packages/cli/src/cli.ts:198`) is representable - task 29 deletes `runPds` and depends on it.
- [ ] Declare the init contributor's surface here, because tasks 13 and 47 both write against it and it must have one home: `PluginInitIo` with `isInteractive`, a `logger: PluginLogger`, and `ask(question: PluginQuestion): Promise<string>` over a `PluginQuestion` (`prompt`, optional `defaultValue`, `required`, `validate`) that generalises `packages/cli/src/init.ts:16-40`; an unanswered optional question resolves to the empty string, never `undefined`.
- [ ] Declare `ConfigBlockEntry` (`property`, optional `comment`) mirroring the entry shape `renderConfig` builds at `packages/cli/src/init.ts:48-65`, and type `init?(io: PluginInitIo): Promise<ConfigBlockEntry[]>` so a contributor that the operator declines returns an empty array rather than `undefined` (DEVELOPMENT.md §Error handling - no null for a domain value).
- [ ] Declare `Plugin<TConfig = never>` with exactly `name`, `description`, `commands`, optional `nodes(ctx: PluginContext<TConfig>): ResourceNode[]`, optional `configKey`, optional `validateConfig(raw: unknown): TConfig` and optional `init(io)` - no lifecycle hooks, no plugin-to-plugin dependencies, no contributed ports, no merged config schema beyond the one owned key. State in a doc comment that the host's registry is `Plugin<unknown>[]`, that a `Plugin<PdsConfig>` and a `Plugin<AnalyticsConfig>` both join it because `run` and `nodes` are method-declared and therefore bivariant, and that the host consequently builds a `PluginContext<unknown>` and dispatches through the registry - the reason dispatch needs no cast. Say plainly in the same comment that a `PluginContext<never>` is never constructed and could not be: nothing inhabits `never`, so `pluginConfig` would have no value, and reaching one would take the `as` cast DEVELOPMENT.md bans. For a plugin owning no `configKey` the host puts an empty object there (task 19), per the no-null rule.
- [ ] Declare `PluginManifest` as `{ plugin: string }` and the module-level `PLUGIN_NAME_PATTERN = /^[a-z0-9-]+$/` constant that both the manifest's namespace and `Plugin.name` are checked against, so the spec's JSON fragment and the runtime check cannot drift.
- [ ] Write `validatePlugin(module: unknown, packageName: string): Plugin`: narrow `module` from `unknown`, read its `default` export, and check name, description, `commands` and each command's `action`/`run` in that order, raising an `Error` naming `packageName` and stating what would fix it - and never invoking `nodes`, `init`, `validateConfig` or any `run` while validating.
- [ ] Add `packages/core/src/plugin.test.ts`: one positive case returning a typed `Plugin` from a minimal valid module, one negative case per rejection reason, one case asserting a module whose `nodes()` throws when called still validates, and one asserting no message contains the module's own values.

## Definition of done

- [ ] `Plugin<TConfig = never>` declares exactly `name`, `description`, `commands`, optional `nodes(ctx)`, `configKey`, `validateConfig(raw): TConfig` and `init(io)` - no lifecycle hooks, no plugin-to-plugin dependencies, no contributed ports - and `PluginCommand` carries `action`, `summary` and `run(ctx, args)` with `ctx` typed as `PluginContext<TConfig>` and a multi-word action such as `secret status` representable.
- [ ] The heterogeneous registry compiles without a cast: a type-level test puts a `Plugin<{ a: string }>` and a `Plugin<{ b: number }>` into one `Plugin<unknown>[]` and dispatches a `PluginContext<unknown>` through it, reaching both `run` methods. A second pins the `never` default in the terms that actually hold: a property read off `ctx.pluginConfig` inside a bare `Plugin` (`Plugin<never>`) is `TS2339`, while a whole-field assignment compiles - the second half asserted as documented behaviour, not silently relied on, so nobody later "fixes" it by widening the default to `unknown`.
- [ ] `parseConfigDocument` returns the parsed `OpsConfig` and the raw document, `parseConfig` is its `config` half with an unchanged signature, and a test asserts a document carrying an unknown top-level key round-trips into `raw` while `config` is byte-identical to what `parseConfig` returns today.
- [ ] `PluginInitIo` and its question shape are declared here, `init` returns an empty `ConfigBlockEntry[]` when the operator declines, and `PluginManifest` matches the spec's JSON fragment - a required `plugin` string checked against the shared `PLUGIN_NAME_PATTERN` constant and no additional properties; no `null` or `undefined` stands for a domain value anywhere in the module.
- [ ] `validatePlugin` returns a typed `Plugin` for a minimal valid module and raises for each of: no default export, a non-object default export, a missing or empty `name`, a `name` violating `PLUGIN_NAME_PATTERN`, a missing `description`, `commands` that is not an array, and a command missing `action` or `run` - one negative test each.
- [ ] Every raised message names the offending package and says what would fix it, no message echoes the module's contents, and `validatePlugin` rejects before anything on the module is invoked - proven by a module whose `nodes()` throws when called validating cleanly.
- [ ] Meets the repo definition of done (see plan.md baseline).
- [ ] Reviewable: run `pnpm test -- plugin`; confirm each of the seven negative tests asserts the package name in the expected message, and that `grep -n ': any' packages/core/src/plugin.ts` returns nothing.
