## Steps

- [ ] Add `analytics-error-bucket` ahead of the role: a plain S3 bucket in `us-east-1` for Firehose's failed-record output, created through the plugin bundle's us-east-1 `S3Client` (task 38 - core's `S3Client` built over `ctx.clients.signingUsEast1`, never `ctx.clients.s3`, which signs in `config.region`), named from the same `<env>-<siteName>` derivation the other analytics resources use. It is NOT the site's environment bucket: `S3DestinationConfiguration.BucketARN` matches `arn:.*:s3:::[\w\.\-]{1,255}` - an S3 ARN carries no region, so the API can neither express nor reject a cross-region bucket, and Firehose's cross-region documentation covers only HTTP endpoint destinations. Resting the pipeline on undocumented behaviour is the thing this node avoids.
- [ ] Create the stream with `AppendOnly: true`. `page_views` is insert-only by design, and Firehose scales throughput automatically for append-only Iceberg streams. Whether the flag can be changed afterwards is contested and must not be assumed either way: the Firehose considerations page says it is settable only with `CreateDeliveryStream`, while the `IcebergDestinationUpdate` API reference lists `AppendOnly` among the fields `UpdateDestination` accepts. Write the node defensively - attempt `UpdateDestination` when the recorded flag differs from the configured one, and fall back to deleting and recreating the stream when the update is rejected. Record which path ran in the log line so an operator can see it.
- [ ] Grant the Firehose role write access to the error bucket alone, not to the site's environment bucket, and record in a comment that a schema mismatch sends every affected record there: Firehose errors mismatched records to the S3 error bucket rather than dropping them, so this is a normal path, not a rare one.
- [ ] Write `analytics-firehose-role` with `dependsOn: ['analytics-error-bucket', 'analytics-table', 'analytics-transform-function']` - the three nodes whose recorded outputs its four grants interpolate - creating the delivery role through `ctx.clients.iam.ensureRole` and applying its inline policy from a named helper shared by `create` and `update`, as `packages/cli/src/nodes.ts:180-216` does. `topoSort` drains zero-indegree nodes in alphabetical order (`packages/cli/src/graph.ts:35-38`), so a role declaring `dependsOn: []` is reconciled before the function it grants `lambda:InvokeFunction` on and the policy interpolates an unrecorded output - a wrong permission written silently, never an error. `githubOidcRoleNode` (`packages/cli/src/nodes.ts:830`) is the precedent: it declares `cloudfront-distribution` precisely because its policy reads that node's recorded ARN at `:911`.
- [ ] Grant exactly the four capabilities the spec names, each against a concrete ARN built from `ctx.accountId`, the resolved analytics config and the recorded outputs of earlier nodes: Glue catalog read on the federated catalog, S3 Tables write on the table, `lambda:InvokeFunction` on the transform function ARN recorded by task 50, and `s3:PutObject` on the plugin's own `analytics-error-bucket` - no fifth statement and no `*` resource.
- [ ] Write `analytics-firehose-stream` with `dependsOn: ['analytics-firehose-role', 'analytics-table', 'analytics-catalog-integration', 'analytics-transform-function']`, matching the chain and the "also on" edges the spec's implementation notes state (error-bucket → firehose-role → firehose-stream, so the role edge carries the error bucket transitively), and configure the Iceberg destination plus the record-transform Lambda processor pointing at the recorded function ARN. The role edge is required by the spec's own rule - the stream's `IcebergDestinationConfiguration` interpolates the role's recorded `RoleARN` - and without it the ordering survives only by `topoSort`'s alphabetical accident (`…-role` < `…-stream`, `packages/cli/src/graph.ts:35-38`), the exact coincidence-reliance the spec's note 9 warns against; task 54's edge test asserts the chain.
- [ ] Point the error/backup prefix at the plugin's own `analytics-error-bucket`, never at the site's environment bucket (`ctx.names.bucket`), and add a comment stating why: the site's bucket is in `config.region` while the stream is pinned to `us-east-1`, and Firehose's cross-region behaviour for an S3 destination is undocumented - an S3 ARN carries no region, so the API can neither express nor reject the mismatch. A schema mismatch sends *every* affected record here, so this is a normal path, not a rare one.
- [ ] Implement `read` to describe the stream and hydrate its delivery state into the plugin's scoped state, so task 55 can report health without a second describe path, returning `false` without throwing when the stream is absent.
- [ ] Implement `delete` to remove the stream and then the role, each idempotent, so a re-run after a partial teardown completes rather than failing on the already-deleted half.
- [ ] Extend `packages/analytics/src/nodes.test.ts`: assert the parsed policy document has four statements and no `*` resource; assert the role's and the stream's declared `dependsOn` sets and the stream's destination/processor payload; assert `read` surfaces the delivery state and returns `false` for an absent stream; assert a re-run of `delete` after a partial teardown issues the remaining call and throws nothing.

## Definition of done

- [ ] `analytics-firehose-role` grants exactly the four capabilities the spec names - Glue catalog read, S3 Tables write, `lambda:InvokeFunction` on the transform function, and write to the plugin's own error bucket - each scoped to a concrete ARN, with a test parsing the policy document and asserting no statement uses a `*` resource, no fifth statement exists, and `ctx.names.bucket` appears nowhere in it.
- [ ] Both nodes declare the dependencies their payloads read, matching the spec's stated ordering, and a test asserts each declared set: `analytics-firehose-role` declares `dependsOn: ['analytics-error-bucket', 'analytics-table', 'analytics-transform-function']`, because its policy interpolates an ARN recorded by each of the three and `topoSort` would otherwise reconcile it first; `analytics-firehose-stream` declares `dependsOn: ['analytics-firehose-role', 'analytics-table', 'analytics-catalog-integration', 'analytics-transform-function']` - the role edge because its `IcebergDestinationConfiguration` interpolates the role's recorded ARN (and it carries the error bucket transitively, completing the spec's error-bucket → firehose-role → firehose-stream chain that task 54's edge test asserts) - and configures the Iceberg destination plus the record-transform Lambda processor against the function ARN recorded by task 50 rather than a re-derived name.
- [ ] The error/backup prefix targets the plugin's own `analytics-error-bucket` in `us-east-1`, and a comment states why the site's environment bucket is not reused - it sits in `config.region`, and Firehose's cross-region S3 behaviour is undocumented while an S3 ARN carries no region to reject it. A test asserts the stream's `S3DestinationConfiguration.BucketARN` names the plugin's bucket.
- [ ] The `AppendOnly` reconcile is defensive rather than assumed: the node attempts `UpdateDestination` and falls back to replacing the stream when the update is rejected, with one test per branch, because AWS's own documentation contradicts itself on whether the flag is settable after creation.
- [ ] `read` surfaces the stream's delivery state into the plugin's scoped state so `analytics status` can report health, and returns `false` without throwing when the stream is absent; `delete` is idempotent and re-runnable after a partial teardown - one test each.
