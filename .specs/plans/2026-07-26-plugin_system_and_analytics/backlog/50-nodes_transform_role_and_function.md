## Steps

- [ ] Declare where the plugin resolves its own package directory before reading the bundled transform artifact: add `packages/analytics/src/paths.ts` holding one `import.meta.url`-derived constant, documented as the plugin's composition root and the ONLY file in the package permitted to touch `import.meta.url` — mirroring how the CLI resolves `agentDir` at `packages/cli/src/context.ts:118`. `nodes.ts` is a domain module reached through `plugin.nodes(ctx)` with no wiring step of its own, so resolving the path inline there would satisfy this task's `node:fs` prohibition while breaking DEVELOPMENT.md's composition-root rule. The bytes are still read through `ctx.ports.fs`.
- [ ] Add the `analytics-salt-secret` node ahead of the role: a Secrets Manager secret named from `config.analytics.saltSecretName` (default `<siteName>/<env>/analytics-salt`) holding one long-lived random value, created if absent and never overwritten on reconcile — regenerating it would silently break `visitor_key` comparison across the boundary. Configure NO Secrets Manager rotation: daily turnover comes from `dailySalt(secret, day)` in the transform (task 41), so managed rotation would add a rotation Lambda, a schedule and a second role for no gain. Pass the secret's name to the function as an environment variable. `SecretsManagerClient` already exists in core (`packages/core/src/aws/secretsmanager.ts`), so no new client is needed — but take it from task 38's plugin bundle, which builds one over `ctx.clients.signingUsEast1`, NOT from `ctx.clients.secrets`, which core builds over the primary-region signer (`packages/core/src/clients.ts:68`): the transform Lambda runs in us-east-1 and the role grants `GetSecretValue` on an ARN that embeds a region, so a secret created in `config.region` would leave the function unable to read it. `packages/pds/src/secret.ts` is the precedent for shape and error handling.
- [ ] Write `analytics-transform-role` with `dependsOn: ['analytics-salt-secret']` — the node whose recorded ARN the role's `secretsmanager:GetSecretValue` grant interpolates, and the ordering the spec's implementation notes state. `topoSort` drains zero-indegree nodes in alphabetical order (`packages/cli/src/graph.ts:34-37`), so a role declaring `dependsOn: []` is reconciled before the secret and grants on an undefined ARN — a wrong permission written silently, never an error. Create the role through `ctx.clients.iam.ensureRole` with a Lambda trust document restating the shape at `packages/cli/src/nodes.ts:106-115`, and add a comment stating the duplication is deliberate because `LAMBDA_TRUST` is CLI-private and a plugin may not import the CLI.
- [ ] Apply the role's inline policy in a named helper shared by `create` and `update`, granting `logs:CreateLogStream`/`logs:PutLogEvents` on the function's own log group ARN — the `packages/cli/src/nodes.ts:212` scoping — plus `secretsmanager:GetSecretValue` on the salt secret's ARN ALONE, with no `*` resource anywhere in the document.
- [ ] Declare the function's runtime, handler, timeout and memory as named module constants and reference them from the create and update payloads, never as literals at the call site.
- [ ] Write `analytics-transform-function` with `dependsOn: ['analytics-transform-role']`: read the bundled transform's bytes through `ctx.ports.fs`, zip them the way `packageAndUploadAgent` does at `packages/cli/src/agent-package.ts:48-53`, and record the deployed source hash from task 43 into the plugin's scoped state alongside the function ARN.
- [ ] Decide and record in a comment how the code reaches the function: inline zip bytes rather than an S3 code bucket, because Lambda requires the code bucket to be in the function's own region while the site's bucket is in `config.region` and the function is pinned to `us-east-1`; confirm the inline-payload limit in the `CreateFunction` API reference and guard it with a named constant that raises naming the measured size when the bundle exceeds it.
- [ ] Gate the update on the recorded hash the way `builderImageAction` does at `packages/cli/src/nodes.ts:311-321`: an unchanged hash performs no update call, a changed hash performs one, and the decision is a pure function so it is testable without the AWS calls.
- [ ] Extend `packages/analytics/src/nodes.test.ts`: inspect the policy document for the absence of a `*` resource; assert the unchanged-hash and changed-hash update behaviour; assert `read` returns `false` without throwing when the function is absent and that `create` records the ARN; assert `delete` removes the function then the role and is re-runnable when either is already gone.

## Definition of done

- [ ] `analytics-transform-role` creates a Lambda execution role using the trust shape at `packages/cli/src/nodes.ts:106-115` — restated rather than imported, with a comment saying why — and attaches an inline policy scoped to the function's own log group with no wildcard `Resource`, asserted by a test that inspects the policy document rather than the call count. It declares `dependsOn: ['analytics-salt-secret']`, the node whose recorded ARN that policy interpolates, asserted on the declared set — an undeclared dependency reconciles the role first and grants on `undefined`.
- [ ] `analytics-transform-function` depends on the role and uploads the bundled transform as a zip keyed by task 43's source hash, with runtime, handler, timeout and memory as named constants rather than literals at the call site; a test asserts an unchanged hash performs no update call and a changed hash performs one.
- [ ] `read` reports absence without throwing and `create` records the function ARN into the plugin's scoped state; `delete` removes the function then the role and is re-runnable when either is already gone — asserted in both partial-teardown directions.
- [ ] The salt secret is created in `us-east-1` like every other node the plugin owns: it goes through task 38's bundle client, and a test with `config.region` set to something else asserts the recorded request signed against `/us-east-1/secretsmanager/` and that the ARN the role's policy grants on carries the same region — reusing `ctx.clients.secrets` would put the secret where the transform Lambda cannot read it.
