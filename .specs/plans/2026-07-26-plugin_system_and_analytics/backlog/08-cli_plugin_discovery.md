## Steps

- [ ] Create `packages/cli/src/plugins.ts` with a module comment stating what it owns and recording the collect-versus-throw choice: a broken plugin is a reported failure, not an aborted CLI run, because one bad dependency must not make `blogwright deploy` unusable.
- [ ] Implement `discover(repoRoot, ports)` returning a value type carrying `plugins` and `failures` — both always arrays, never `null` or `undefined` — where each failure names the package and the reason.
- [ ] Read `<repoRoot>/package.json` through `ports.fs.readText` and parse it, raising an error naming the path and what would fix it when the file is absent (`FileNotFoundError`) or unparseable, before any candidate is resolved.
- [ ] Resolve every candidate's `package.json` by resolving the BARE specifier through `ports.loader.resolve` and walking up from the resolved file to the nearest `package.json`. Never resolve `<name>/package.json` directly: every package in this workspace declares an `exports` map that does not list `./package.json`, so Node's exports encapsulation makes that throw `ERR_PACKAGE_PATH_NOT_EXPORTED`. Verified 2026-07-26 — `require.resolve('blogwright-pds/package.json')` throws today while `require.resolve('blogwright-pds')` resolves. Give `ModuleLoader` a `packageJsonPathFor(specifier, fromDir)` operation (task 05) so the walk-up lives in the adapter, not in domain code.
- [ ] Build the candidate set from every `dependencies` and `devDependencies` name starting with `blogwright-`, resolved from `repoRoot`; when the consumer depends on `blogwright` itself, resolve it by the rule above, read its `package.json` through `ports.fs`, and fold its own `blogwright-*` dependencies (`packages/cli/package.json:26-30`) into the candidate set, resolved from the CLI package's directory.
- [ ] For each candidate, read the resolved `package.json` through `ports.fs`: skip silently when there is no `blogwright.plugin` field, record a failure naming the package when the field is malformed (wrong type, or a namespace violating `^[a-z0-9-]+$`), and otherwise `ports.loader.load` the package and pass its default export through core's `validatePlugin`, recording the validator's reason as the failure when it rejects.
- [ ] Add ONE integration test that uses the REAL `ModuleLoader` adapter against this workspace and discovers `blogwright-pds` — no map-backed fake. The map-backed fake cannot model exports encapsulation, so without this test the whole discovery path passes CI and fails for every real install. This test is a precondition of task 29, which deletes `runPds` and makes discovery the only route to `blogwright pds <action>`.
- [ ] Write `packages/cli/src/plugins.test.ts` over `createMemoryFileSystem` and a map-backed `ModuleLoader` fake, covering the absent and unparseable `package.json`, the non-matching dependency, the bundled plugin, the missing manifest field, the malformed manifest, and the failing default export.

## Definition of done

- [ ] `<repoRoot>/package.json` is read through `ports.fs` and an absent or unparseable file raises an error naming the path and what would fix it (negative tests); both `dependencies` and `devDependencies` are considered, and only names starting with `blogwright-` become candidates — a test with a non-matching dependency proves it is never resolved through the loader.
- [ ] The candidate set is the UNION of the consumer's `blogwright-*` deps and the `blogwright` package's own dependencies — verified against this repo, whose root `package.json` has zero `blogwright-*` entries, so a consumer-only scan finds nothing and `blogwright pds` would break at task 29. Plugins that ship as dependencies of the CLI itself are discovered too: a test proves a bundled plugin is discovered from a consumer `package.json` that lists only `blogwright`, because a consuming repo depends on `blogwright`, not on `blogwright-pds`, and `blogwright pds sync` must keep working for every user once task 29 deletes `runPds`.
- [ ] A candidate whose `package.json` has no `blogwright.plugin` field is skipped silently with no error and no load (the test asserts the loader's `load` was not called for it); a candidate whose manifest field is malformed (wrong type, or a namespace violating `^[a-z0-9-]+$`) and a candidate whose default export fails `validatePlugin` are each reported as a load failure naming the package and carrying the reason.
- [ ] `discover` returns a value type carrying loaded plugins and failures with no `null`/`undefined` for either collection, the collect-versus-throw choice is stated in the module comment, and the module imports only ports and core — no `node:fs`, no `node:module` — as `pnpm lint` verifies.
- [ ] Meets the repo definition of done (see plan.md baseline).
- [ ] Candidate `package.json` files are located by resolving the bare specifier and walking up, never by resolving `<name>/package.json`; one integration test using the real `ModuleLoader` adapter discovers `blogwright-pds` from this workspace and passes. Reviewable: temporarily change the resolver to `<name>/package.json` and confirm that integration test fails with `ERR_PACKAGE_PATH_NOT_EXPORTED` while every fake-backed test still passes — that gap is exactly what the integration test exists to close.
- [ ] Reviewable: run `pnpm --filter blogwright test -- plugins`; confirm every unit case runs against `createMemoryFileSystem` and a map-backed `ModuleLoader` fake with no disk or registry access, that the one integration case is clearly marked as using the real adapter, and that the bundled-plugin case passes with a consumer `package.json` whose only dependency is `blogwright`.
