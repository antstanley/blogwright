## Steps

- [ ] Add `packages/pds/src/nodes.ts` exporting `buildPdsNodes(ctx)`. This is the first time pds contributes graph nodes; the module comment says why the grant lives here rather than in the site graph. The wiring to the plugin's `nodes(ctx)` member is task 25's, which depends on this task — so the node is exercised by its own tests here and reaches the engine there.
- [ ] The single node `pds-oidc-policy` calls `putRolePolicy(ctx.names.githubRole, 'blogwright-pds', …)` — the **package** name, which is the SPI's convention for an inline-policy name because the name is on-the-wire state `delete()` finds again through `listRolePolicies`, not the `pds` namespace, which a manifest can re-declare — with the same three actions the site grants today — `secretsmanager:GetSecretValue`, `PutSecretValue`, `CreateSecret` — on `arn:aws:secretsmanager:<region>:<account>:secret:<resolved secret name>-*`, resolving the name through task 21's `resolvePdsSecretName` rather than reading `config.pds.secretName` directly.
- [ ] `read()` returns whether the policy name is present via `listRolePolicies`; `delete()` calls `deleteRolePolicy`. Because the policy is separately named, creating and deleting it never touches the site's own inline policy document.
- [ ] Add a `githubRole` field, `` `${prefix}-gh` ``, to `Names` (`packages/core/src/config.ts:333-345`) and `deriveNames` (`:360-372`), and have `githubOidcRoleNode` read `ctx.names.githubRole` instead of deriving it privately at `packages/cli/src/nodes.ts:826`. The derived value is unchanged, so no role is renamed — assert that with a test pinning `deriveNames('production', …).githubRole`. Without this the plugin would re-derive a name that lives in a CLI-private lambda, and only the role's ARN reaches state (`nodes.ts:966`).
- [ ] Read the role name from `ctx.names.githubRole` and confirm the role's ARN is recorded in `ctx.siteState` before any call, failing with a message naming `blogwright bootstrap` when `githubRepo` is set but the role is absent. Record the node's outputs through `ctx.record()`.
- [ ] Skip the node entirely when `config.pds` is absent or when `config.githubRepo` is unset. A site with no CI deploys has no OIDC role at all — the site graph only adds `githubOidcRoleNode` for a non-preview stack when `githubRepo` is set (`packages/cli/src/nodes.ts:1082`) — so that is a fully bootstrapped site, not an error, and `pds bootstrap` is a no-op there.
- [ ] Write `packages/pds/src/nodes.test.ts` over a recording IAM client: the policy name, the three actions and the ARN pattern are asserted byte-identical to the statement `oidcRolePolicyStatements` produces today (copy the expectation from `packages/cli/src/nodes.test.ts:194-208`), so the move is provably behaviour-preserving; plus the absent-config, absent-githubRepo and site-not-bootstrapped cases.

That statement is what covers a deployed stack until an operator runs `blogwright pds bootstrap`, so it stays until task 59, a release later; task 27's inline default is what keeps its ARN total in between.
