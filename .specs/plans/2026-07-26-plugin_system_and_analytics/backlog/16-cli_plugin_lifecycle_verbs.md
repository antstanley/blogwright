## Steps

- [ ] Decide the precedence and write it into the module comment of `packages/cli/src/plugin-commands.ts`: `bootstrap` and `destroy` are always the generic verbs, because a plugin may not import the CLI and therefore cannot run the engine itself, so a plugin declaring either is rejected with an error naming the plugin and the colliding action; `status` is the generic verb unless the plugin declares one, because `read()` lives on the plugin's own nodes.
- [ ] Add the rejection to the boundary check the discovery path already runs (`validatePlugin` from task 03, or the collision pass from task 09) so a bad plugin fails at load with the collision named, not mid-command.
- [ ] Build the plugin's context in `plugin-commands.ts` from the `OpsContext` `createContext` returns, populating BOTH state surfaces from different stores: `siteState` is the unscoped store's already-loaded `state` (the site's `state/<env>.json`, passed through read-only and never written), while `store` becomes a `StateStore` scoped to the plugin's `name`, `state` becomes that scoped store's own `load()`, and `record()` writes into it. Every other field — clients, ports, names, tags, logger — passes through as-is, and `save()` re-points at the scoped store. Do not overwrite `siteState` with the scoped load; task 53's log-delivery node reads the site's distribution outputs through it and cannot find them in `state/<env>.analytics.json`.
- [ ] Implement the three verbs over `plugin.nodes(ctx)`: `bootstrap` calls `applyGraph`, `destroy` refuses without `--yes` with the same message shape as `commands.ts:56` then calls `destroyGraph` followed by the scoped `store.delete()`, and `status` calls task 15's extracted read loop and renders through the same interactive/plain branch.
- [ ] Gate all three on `plugin.nodes` being declared: a plugin without it does not gain the verbs, and asking for one lists the plugin's real actions and exits non-zero.
- [ ] Write `packages/cli/src/plugin-commands.test.ts` cases with a fake node-contributing plugin and a recording S3 client, asserting the state keys touched by a plugin bootstrap and, separately, by `blogwright bootstrap` and `blogwright destroy` with that plugin installed.
- [ ] Write the changeset recording the three new user-facing verbs and the precedence rule.

## Definition of done

- [ ] `blogwright <plugin> bootstrap|status|destroy` reconcile, read and tear down the plugin's `nodes(ctx)` set using the CLI's existing engine, and no second implementation of `topoSort`/`applyGraph`/`destroyGraph` exists — `grep -rn "function topoSort\|function applyGraph\|function destroyGraph" packages/` returns only `packages/cli/src/graph.ts`.
- [ ] Precedence is decided, recorded in `plugin-commands.ts`'s module comment and tested in both directions: a plugin declaring `bootstrap` or `destroy` is rejected at load with an error naming the plugin and the collision, and a plugin declaring `status` gets its own command while one that does not gets the generic verb — the constraint that forces this is that a plugin may not import the CLI and so cannot run the engine itself, and task 47's command table is written against whatever is chosen here.
- [ ] State isolation holds in both directions: the context the plugin verbs receive carries a `StateStore` scoped to the plugin's name with its own loaded state (a test asserts the only state key written during a plugin bootstrap is `state/<env>.<plugin>.json`), and `blogwright bootstrap` and `blogwright destroy` with a node-contributing plugin installed neither include plugin nodes nor read or write plugin state (a test asserts `buildNodes` output and the touched state keys are unchanged from today).
- [ ] The refusal space is covered: `<plugin> destroy` without `--yes` raises with the same contract as the site verb (`commands.ts:56`) and destroys nothing, and a plugin with no `nodes` contributor does not gain these verbs — asking for one lists the plugin's real actions and exits non-zero — one test each.
- [ ] Meets the repo definition of done (see plan.md baseline).
- [ ] Reviewable: run `pnpm test -- plugin-commands`; confirm the recording S3 client shows exactly one state key for a plugin bootstrap, that it is `state/<env>.<plugin>.json`, and that the site-bootstrap test with the same plugin installed shows only `state/<env>.json`.
