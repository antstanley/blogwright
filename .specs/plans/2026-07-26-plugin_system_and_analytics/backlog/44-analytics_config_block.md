## Steps

- [ ] Every derived default carries the environment: `tableBucket` defaults to `<env>-<siteName>-analytics` and `saltSecretName` to `<siteName>/<env>/analytics-salt`, matching `deriveNames`' `<env>-<siteName>` prefix at `packages/core/src/config.ts:352`. Without the env, staging and production write into one Iceberg table and `blogwright analytics destroy --yes` in staging runs `DeleteTableBucket` on production's data - scoped state (`state/<env>.analytics.json`) cannot detect the collision. Add a test asserting two different envs produce two different bucket names and two different secret names.
- [ ] Carry `saltSecretName` in `AnalyticsConfig`, defaulting to `<siteName>/<env>/analytics-salt` and validated against the same character class `pds.secretName` uses (`^[\w/+=.@-]+$`). The salt decision settled 2026-07-26 on a Secrets Manager secret; task 50's node reads this field for the secret's name.
- [ ] Declare `AnalyticsConfig` in `packages/analytics/src/config.ts` matching the spec's `$defs.AnalyticsConfig`: `tableBucket`, `namespace`, `table`, `bots` as `'flag' | 'filter'`, and `dashboard.port`, every optional field expressed as `?: T | undefined` under `exactOptionalPropertyTypes`.
- [ ] Declare the defaults and limits as named module constants - the `namespace` default `web`, the `table` default `page_views`, the `bots` default `flag`, the dashboard port default `4317`, the bucket-name pattern and length bounds, and the port bounds - with the dashboard port default exported as the single constant the dashboard server (task 56) also reads.
- [ ] Write the resolver that merges a raw block over the defaults and derives `tableBucket` as `<env>-<siteName>-analytics`, so a block of `{}` yields a fully populated resolved config.
- [ ] Write `validateAnalyticsConfig(raw)` raising in the repo's vocabulary - `config.analytics.<key> …, got <value>` - for a bucket outside `^[0-9a-z-]{3,63}$`, a `namespace` or `table` outside `^[a-z0-9_]+$`, a `bots` value outside the union, a port outside `1024..65535`, and any unknown key inside the block.
- [ ] Write `packages/analytics/src/config.test.ts`: the `{}`-validates-with-every-default case; boundary cases at 2/3/63/64 characters and 1023/1024/65535/65536; the four rejection cases; a case asserting two environments derive two different bucket names and two different salt-secret names; and a case feeding a config carrying an `analytics` block through core's `parseConfig` unchanged.

## Definition of done

- [ ] `AnalyticsConfig` matches the spec's `$defs.AnalyticsConfig` - `tableBucket`, `namespace` (default `web`), `table` (default `page_views`), `bots` (`'flag' | 'filter'`, default `flag`), `dashboard.port` (default `4317`) - a test asserts a block of `{}` validates and produces every default, and every default and limit is a named module constant rather than a literal at the call site, with the dashboard port default a single constant shared with the dashboard server.
- [ ] One table bucket per environment, as the spec's §Configuration settles it: `tableBucket` defaults to `<env>-<siteName>-analytics` and `saltSecretName` to `<siteName>/<env>/analytics-salt`, both carrying the environment. A test asserts two environments derive two different bucket names and two different secret names, and the module's doc comment records the consequence a reader must not undo - without the environment, `blogwright analytics destroy --yes` in staging runs `DeleteTableBucket` against production's data.
- [ ] Validity-boundary tests cover one below / at / one above each limit - `tableBucket` at 2, 3, 63 and 64 characters against `^[0-9a-z-]{3,63}$`, and `dashboard.port` at 1023, 1024, 65535 and 65536 - alongside negative-space tests rejecting a `namespace` or `table` outside `^[a-z0-9_]+$`, a `bots` value outside the union, and an unknown key inside the block (`additionalProperties: false`), with every error message naming the offending key and value in the repo's vocabulary, e.g. `config.analytics.dashboard.port must be in 1024..65535, got 80`.
- [ ] Absence is expressed with `?: T | undefined` and no function returns or accepts `null` for a domain value; a test asserts a config carrying an `analytics` block passes core's `parseConfig` (`packages/core/src/config.ts:242`) untouched when the plugin is not loaded - valid and inert.
- [ ] Meets the repo definition of done (see plan.md baseline).
- [ ] Reviewable: run `pnpm test -- config` inside `packages/analytics`; confirm the `{}` case asserts every default by name and that each of the eight boundary cases appears as its own named test with the value in the test name.
