## Steps

- [ ] Split `USAGE` (`packages/cli/src/cli.ts:11-63`) into the static base text and a `buildHelp(base, discovered)` function that returns the base unchanged when nothing was discovered, so the no-plugins path is textually identical to today.
- [ ] Append one section per plugin, headed by the plugin's `description` and listing one line per command from its `action` and `summary`, ordered deterministically by plugin name so help output does not vary with dependency-map iteration order.
- [ ] Render each failed load as a single line naming the package and the reason, with no stack trace, so one broken plugin cannot break `blogwright --help`.
- [ ] Run discovery in the help branch (`packages/cli/src/cli.ts:102-106`) and record in the module comment which paths pay for discovery and why: generic plugin dispatch, `blogwright --help` and a bare invocation, `blogwright plugin list` (task 17, which must name plugins that failed to load) and `blogwright init` (task 14, whose wizard asks each discovered plugin's questions) - every other built-in command loads no plugin module, `deploy`, `bootstrap` and `status` among them (so are `rollback`, `delete`, `destroy`, `history`, `logs` and `preview`; the three named are the ones task 10's laziness test pins). Help is the case this task owns, because task 29 removes the static `pds` block at `:33-47` and `blogwright --help` must still list all six pds actions.
- [ ] Feed the assembled text to every existing `USAGE` print site (`packages/cli/src/cli.ts:103,119,171,200,256,288`) so the error paths show the same help as the help path, leaving their exit codes untouched.
- [ ] Extend `packages/cli/src/cli.test.ts`: the no-plugins output still matches the task-07 byte-exact pin; `--help` runs discovery; two fake plugins render two deterministically ordered sections; a failed load leaves the remaining sections rendered; the `--help` and bare-invocation exit codes are unchanged.

## Definition of done

- [ ] The laziness tension is resolved in one direction and the direction is forced: `--help` and a bare invocation run discovery, a test asserts it, and the module comment records the full set of paths that do - dispatch, help, `blogwright plugin list` and `blogwright init` - against the built-in commands that do not, `deploy`, `bootstrap` and `status` among them (every built-in other than the four discovery paths pays nothing, exactly as the spec phrases it). The pds migration requires `blogwright --help` to still list all six pds actions once the static `pds` block leaves `USAGE` at task 29, which is impossible if `--help` skips discovery.
- [ ] With no plugins installed, `blogwright --help` output is byte-identical to today's `USAGE` string, asserted against the pinned test from task 07 so existing users see no churn, and the exit codes for `--help` and for a bare invocation are unchanged.
- [ ] With plugins installed, one section per plugin is appended showing the plugin's `description` and one line per command from its `action` plus `summary` - tested over two fake plugins in a deterministic order.
- [ ] A plugin that failed to load does not break `--help`: the remaining sections still render and the failure is surfaced without a stack trace (test).
- [ ] Meets the repo definition of done (see plan.md baseline).
- [ ] Reviewable: run `pnpm --filter blogwright test -- cli`; confirm the no-plugins case still matches the byte-exact `USAGE` pin from task 07, that two fake plugins render in name order regardless of fixture order, and that a fake plugin whose module throws on load leaves the other plugin's section rendered.
