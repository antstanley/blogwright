# Task 31 — Open the transport so a plugin can supply its own AWS services

**Plan:** [plan.md](../plan.md) · **Certificate:** [31-core_transport_seam-certificate.md](31-core_transport_seam-certificate.md)

**Implements:** [2026-07-26-cli_plugin_system.md §Plugin SPI → Plugin-supplied AWS services (Add)](../../../changes/2026-07-26-cli_plugin_system.md) (`SendOptions.service` accepts a service descriptor as well as a core key, so a plugin reaches a service core does not enumerate)
**Depends on:** —
**Produces:** `resolveEndpoint` and `SendOptions.service` accept a `{ service, signingName, global? }` descriptor as well as today's `ServiceKey`, so a plugin can sign against any AWS service without an edit to core — with every existing core client's request provably byte-identical
**Pointers:** `packages/core/src/aws/endpoint.ts:19-31` (the `SIGNING_NAMES` map, which stays byte-identical), `packages/core/src/aws/endpoint.ts:27-29` (the `microvms: 'lambda'` entry and its comment, the regression anchor), `packages/core/src/aws/endpoint.ts:33` (`ServiceKey`, derived from the map), `packages/core/src/aws/endpoint.ts:36` (`GLOBAL_SERVICES`, a `Set<ServiceKey>` that must keep accepting only core's keys while a descriptor carries its own `global` flag), `packages/core/src/aws/endpoint.ts:63,75` (`canonicalHost`, whose parameter widens to `string`, and its `default` branch `` `${service}.${region}.amazonaws.com` ``, which does not change), `packages/core/src/aws/endpoint.test.ts:6,16,24` (the three existing describes the new assertions join), `packages/core/src/aws/signer.ts:27` (`SendOptions.service`), `packages/core/src/aws/signer.ts:96,124` (`resolveEndpoint` and `SIGNING_NAMES[opts.service]` — the signing name), `packages/core/src/aws/signer.ts:135` (`uriEscapePath: opts.service !== 's3'` — the site that keys off the union and silently takes the wrong branch for a descriptor), `packages/core/src/aws/signer.ts:163,171,193` (`parseError(opts.service, response)`, its `service: string` parameter, and the `new AwsError({ service, … })` that parameter ends up in — the fourth site, and the one that breaks the build)

## Steps

- [ ] Add a `ServiceDescriptor` type to `packages/core/src/aws/endpoint.ts` — `{ service: string; signingName: string; global?: boolean }` — and widen `resolveEndpoint`'s first parameter to `ServiceKey | ServiceDescriptor`, resolving a key through `SIGNING_NAMES` exactly as today and a descriptor through its own fields. Widen `canonicalHost`'s parameter (`endpoint.ts:63`) to `string`, because `resolveEndpoint` now hands it a resolved name rather than a `ServiceKey`; its `switch` branches and its `default` `` `${service}.${region}.amazonaws.com` `` (`:75`) are unchanged, so a descriptor for an unknown service resolves correctly with no new host logic.
- [ ] Export ONE resolution helper — the function that turns `ServiceKey | ServiceDescriptor` into `{ name, signingName, global }` — and make every site that keys off `service` read it. There are four, and they do not all want the same field: get this wrong in one place and the failure is silent.
- [ ] Widen `SendOptions.service` (`packages/core/src/aws/signer.ts:27`), and feed the helper's **signing name** to the `SIGNING_NAMES[opts.service]` lookup (`:124`). `GLOBAL_SERVICES` (`endpoint.ts:36`) stays the source of truth for core's own keys; a descriptor carries its own `global` flag.
- [ ] Feed the helper's **service name** to `uriEscapePath: opts.service !== 's3'` (`packages/core/src/aws/signer.ts:135`), not the raw `ServiceKey | ServiceDescriptor`. A descriptor is never `'s3'` by identity, so left as written it silently takes the non-S3 escaping branch for every plugin-supplied service — a wrong signature, not a crash. Assert the resolved name is what the comparison sees.
- [ ] Feed the helper's **service name** to `parseError(opts.service, response)` (`packages/core/src/aws/signer.ts:163`) — the fourth site, and the only one that breaks the build rather than failing silently: `parseError`'s parameter is already `string` (`:171`), so widening `opts.service` yields `TS2345: Argument of type 'Service' is not assignable to parameter of type 'string'`. Do NOT silence it by widening the parameter to the union: `parseError` passes `service` straight into `new AwsError({ service, … })` (`:193`), so every AWS error raised for a plugin-supplied service would carry `[object Object]` where the service name belongs — losing exactly the error context DEVELOPMENT.md §Error handling requires, and losing it only on the paths no core test covers.
- [ ] Leave `SIGNING_NAMES` closed around the services core itself uses — do NOT add `s3tables`, `firehose`, `glue` or `lambda`. They belong to the analytics plugin (tasks 33–36), which supplies them as descriptors; adding them here would put plugin-specific surface in core and `pnpm knip` would report four exported clients nothing in core or the CLI consumes. The names may appear in `endpoint.test.ts` as descriptor fixtures — that is this task's regression coverage; what may not appear is a new key on the map.
- [ ] Extend `packages/core/src/aws/endpoint.test.ts` (`:6,16,24`) with descriptor cases: an unknown regional service resolves to `<service>.<region>.amazonaws.com` under its own signing name; a descriptor with `global: true` signs in `us-east-1`; an endpoint override still routes a descriptor to the override origin. Assert `microvms` (`endpoint.ts:27-29`, signing name `lambda`, `/2025-09-09/` paths) is untouched.
- [ ] Prove no core client's wire format moved: extend the signer test so a request built from a `ServiceKey` and the equivalent descriptor produce byte-identical canonical requests and `Authorization` headers.
- [ ] Keep `SIGNING_NAMES` at `packages/core/src/aws/endpoint.ts:19-31` byte-identical, `microvms: 'lambda'` (`:29`) and the two-line comment above it included, and confirm it with the regression assertion below — `ServiceKey` at `:33` must not widen by one key.
- [ ] Extend the `uses canonical hosts without an override` test at `packages/core/src/aws/endpoint.test.ts:6` with descriptors for `s3tables`, `firehose`, `glue` and `lambda` against `us-east-1`, keeping the existing `microvms` assertion at `:11` in place as the regression anchor and adding an assertion that `SIGNING_NAMES.microvms` is still `'lambda'`.
- [ ] Add a negative-space test asserting a descriptor with no `global` flag signs in the region passed rather than being forced to `us-east-1` (the behaviour the `GLOBAL_SERVICES` test at `:16` pins for `iam`/`cloudfront`), and extend the override test at `:24` so a descriptor routes to `http://localhost:4566` with `override: true`.

## Definition of done

- [ ] `resolveEndpoint` and `SendOptions.service` accept a `{ service, signingName, global? }` descriptor as well as today's `ServiceKey`, and the absence of a match is impossible by construction — a descriptor carries everything resolution needs.
- [ ] `SIGNING_NAMES` is byte-identical to today: it gains NO keys, and no `s3tables`, `firehose` or `glue` name enters core's non-test source. `grep -rn "s3tables\|firehose\|glue" packages/core/src --include='*.ts' --exclude='*.test.ts'` returns nothing — those services belong to the analytics plugin, which supplies them as descriptors. The gate excludes `*.test.ts` deliberately: the descriptor cases this task adds to `packages/core/src/aws/endpoint.test.ts` name all four services and are the regression coverage, not a leak. `lambda` is excluded from the claim entirely — `SIGNING_NAMES.microvms` is `'lambda'` by design (`endpoint.ts:29`), and the name already appears in `endpoint.ts`, `microvms.ts` and `config.ts`, all of which stay byte-identical.
- [ ] A descriptor for an unknown regional service resolves to `<service>.<region>.amazonaws.com` under its own signing name; a descriptor with `global: true` signs in `us-east-1`; an endpoint override routes a descriptor to the override origin with `override: true` — one test each.
- [ ] `microvms` is provably undisturbed: a regression test asserts it still resolves to `lambda.<region>.amazonaws.com`, signs as `lambda`, and addresses the `/2025-09-09/` paths.
- [ ] All four `service` sites read one resolution helper and each reads the right field: `SIGNING_NAMES[opts.service]` (`signer.ts:124`) the signing name, `uriEscapePath` (`:135`) and `parseError` (`:163`) the service name, and `GLOBAL_SERVICES`/the descriptor's `global` flag the region. `uriEscapePath` is tested in both directions — a descriptor whose service is `s3` gets `false`, every other descriptor gets `true` — so a plugin-supplied service cannot silently take the wrong escaping branch.
- [ ] A failing request for a plugin-supplied service raises an `AwsError` whose `service` is the descriptor's service name, not `[object Object]` and not the descriptor object: a test drives a transport returning a 400 for a descriptor-built request and asserts the raised error's `service` field and message, so `parseError`'s parameter is provably still a `string` carrying a name.
- [ ] No core client's wire format moved: a signer test asserts a request built from a `ServiceKey` and from the equivalent descriptor produce byte-identical canonical requests and `Authorization` headers.
- [ ] Meets the repo definition of done (see plan.md baseline).
- [ ] Reviewable: run `pnpm test -- endpoint` and `jj diff packages/core/src/aws/endpoint.ts`; confirm the descriptor tests cover the regional, global and override paths plus `microvms`, and that the diff touches `SIGNING_NAMES` not at all.
