# Task 01 — Declare PluginContext in blogwright-core

**Plan:** [plan.md](../plan.md) · **Certificate:** [01-core_plugin_context-certificate.md](01-core_plugin_context-certificate.md)

**Implements:** [2026-07-26-cli_plugin_system.md §Plugin SPI → `PluginContext` (Add)](../../../changes/2026-07-26-cli_plugin_system.md) (the narrow slice of the host CLI's context a plugin command receives, satisfied structurally by `OpsContext` so no plugin imports a CLI type)
**Depends on:** —
**Produces:** `PluginContext`, `PluginLogger`, `PluginPorts` and `SiteState` declared in `packages/core/src/plugin.ts` and exported from core's index, plus a test in the CLI that fails the build the moment `OpsContext` stops satisfying `PluginContext`
**Pointers:** `packages/core/src/plugin.ts` (new — the SPI module lives here), `packages/cli/src/context.ts:25-51` (`OpsContext`, the shape being narrowed; `agentDir` at :40 and `save()` at :50 are the two fields deliberately left out), `packages/core/src/state.ts:3,5,25` (`ResourceOutputs`, `OpsState`, `StateStore`), `packages/core/src/config.ts:333,343` (`Names` and its `deliverySource` field, which task 52 reads), `packages/core/src/clients.ts:21` (`AwsClients`), `packages/core/src/ports.ts:12,34` (`FileSystem` and `Terminal`, the two shared ports `PluginPorts` names), `packages/cli/src/logger.ts:9` (`Logger` — the five-method shape `PluginLogger` restates in core), `packages/pds/src/context.ts:10,19,25` (`PdsLogger`/`PdsPorts`/`PdsContext` — the existing precedent, untouched by this task), `packages/core/src/index.ts:22-23` (the barrel; `./plugin.js` sorts between `./config.js` and `./ports.js`), `packages/cli/src/context.test.ts:57` (end of file — where the assignability test goes)

## Steps

- [ ] Create `packages/core/src/plugin.ts` opening with a module comment stating that it owns the plugin SPI vocabulary, that a plugin depends on `blogwright-core` and never on the CLI, and that the CLI's `OpsContext` is deliberately wider than what a plugin is handed.
- [ ] Declare `PluginLogger` with `info`/`step`/`ok`/`warn`/`error` (the shape `packages/cli/src/logger.ts:9` already has and `packages/pds/src/context.ts:10` duplicates) and `PluginPorts` with `fs: FileSystem` and `terminal: Terminal` from `packages/core/src/ports.ts:12,34` — the two shared ports a plugin may cross.
- [ ] Declare `SiteState` as `{ readonly resources: Readonly<Record<string, ResourceOutputs>> }` over `ResourceOutputs` (`packages/core/src/state.ts:3`), the read-only view of the site's recorded resource outputs; `OpsState` (`state.ts:5`) satisfies it because a mutable property is assignable to a `readonly` one, so the CLI needs no wrapper object.
- [ ] Declare `PluginContext` with exactly `env`, `domain`, `preview`, `config: OpsConfig`, `names: Names`, `accountId`, `clients: AwsClients`, `ports: PluginPorts`, `tags`, `logger: PluginLogger`, `store: StateStore` (the plugin's own scoped store, from task 04), `state: PluginOutputs` (the plugin's own recorded outputs), `siteState: SiteState` (the read-only site view) and `record(nodeId, outputs)` — and nothing else; `agentDir` (`packages/cli/src/context.ts:40`) and `save()` (`:50`) stay CLI-internal.
- [ ] Declare `record(nodeId: string, outputs: ResourceOutputs): void` on `PluginContext` as the ONLY way a plugin's resource nodes record outputs, writing into the plugin's own `state`. Doc-comment it against `packages/cli/src/nodes.ts:20-22` (the private `output(ctx, id)` helper it mirrors) and state the rule it exists to enforce: a node must never call `store.save()` itself, because `applyGraph` (`packages/cli/src/graph.ts:84`) saves the in-memory state after every node and would clobber a direct write with stale data.
- [ ] Declare `PluginOutputs` as the plugin's own mutable `Record<string, ResourceOutputs>` — distinct from `SiteState`, which is readonly. The two must not be the same type: tasks 48/50/51 write through the former while task 52 reads the latter, and conflating them is the defect this task exists to prevent.
- [ ] Doc-comment every exported symbol and every `PluginContext` field with what a plugin may rely on, naming the load-bearing consumers: `names.deliverySource` (`packages/core/src/config.ts:343`) and the site's recorded distribution outputs feed the analytics log-delivery node in task 52, and `accountId` builds the analytics IAM role ARNs.
- [ ] Add `export * from './plugin.js';` to `packages/core/src/index.ts` in the barrel's alphabetical position, between `./config.js` (:22) and `./ports.js` (:23).
- [ ] Add the compile-time proof at the end of `packages/cli/src/context.test.ts`: assign `createTestContext()` to a binding annotated `PluginContext` imported from `blogwright-core`, with no cast and no `any`, and assert one field so the test has a runtime body as well as a type-level one.

## Definition of done

- [ ] `PluginContext` names exactly `env`, `domain`, `preview`, `config`, `names`, `accountId`, `clients`, `ports`, `tags`, `logger`, the plugin's own scoped `store`, `state` (the plugin's own outputs), `siteState` (the read-only site view), and `record()` — and nothing more; `agentDir` and `save()` are absent by decision, recorded in the module's doc comments.
- [ ] `state` and `siteState` are separate fields of separate types, and a test proves the distinction: a `ResourceNode<PluginContext>` calls `ctx.record('n', { arn: 'a' })`, the value is readable back from `ctx.state`, and `ctx.siteState` is unaffected. Without this test the two fields drift back together at task 16.
- [ ] `names`, `accountId` and the site-state view are justified in doc comments by their actual consumers (task 52's log-delivery node reading `names.deliverySource` and the site's distribution outputs; the analytics IAM roles reading the account id), so a later reader cannot mistake them for speculative surface, and every exported symbol carries a doc comment (DEVELOPMENT.md §Documentation).
- [ ] `siteState` is `readonly` in the type, so `ctx.siteState.resources['x'] = {}` does not typecheck and a plugin can never write `state/<env>.json` — `record()` into the plugin's own scoped state is the only state surface it may write through; `packages/core/src/plugin.ts`'s import list names only core modules (`./clients.js`, `./config.js`, `./ports.js`, `./state.js`) and no CLI or pds module, and `packages/pds/src/context.ts` is untouched, because narrowing `PdsContext` is task 24.
- [ ] A test in `packages/cli/src/context.test.ts` assigns a `createTestContext()` result to a `PluginContext` binding with no cast and no `any`, so the structural claim fails the build if it stops holding.
- [ ] Meets the repo definition of done (see plan.md baseline).
- [ ] Reviewable: run `pnpm build && pnpm test -- context`, then add to `PluginContext` a field `OpsContext` does not have and confirm `pnpm typecheck` fails inside `packages/cli/src/context.test.ts` — the assignment is a real gate, not a comment.
