# Task 01 — Declare PluginContext<TConfig> in blogwright-core

**Plan:** [plan.md](../plan.md) · **Certificate:** [01-core_plugin_context-certificate.md](01-core_plugin_context-certificate.md)

**Implements:** [2026-07-26-cli_plugin_system.md §Plugin SPI → `PluginContext` (Add)](../../../changes/2026-07-26-cli_plugin_system.md) (the narrow slice of the host CLI's context a plugin command receives, satisfied structurally by `OpsContext` so no plugin imports a CLI type)
**Depends on:** —
**Produces:** `PluginContext<TConfig>`, `PluginLogger`, `PluginPorts` and `SiteState` declared in `packages/core/src/plugin.ts` and exported from core's index, plus a test in the CLI that fails the build the moment a `PluginContext` member stops being suppliable — thirteen of the sixteen from an `OpsContext`, the other three from the dispatch boundary
**Pointers:** `packages/core/src/plugin.ts` (new — the SPI module lives here), `packages/cli/src/context.ts:25-51` (`OpsContext`, the shape being narrowed; `agentDir` at :40 is CLI-side, and `ports` at :38 is the CLI's four-member `Ports`, not `PluginPorts`), `packages/cli/src/ports.ts:9,21,25` (`Vcs`, `PingBuilder` and the `Ports` interface — CLI-private, which is why `PluginPorts` is a separate core declaration), `packages/core/src/state.ts:3,5,25` (`ResourceOutputs`, `OpsState`, `StateStore`), `packages/core/src/config.ts:333,343` (`Names` and its `deliverySource` field, which task 53 reads), `packages/core/src/clients.ts:21` (`AwsClients`), `packages/core/src/ports.ts:12,34` (`FileSystem` and `Terminal`, the two shared ports `PluginPorts` names), `packages/cli/src/logger.ts:9` (`Logger` — the five-method shape `PluginLogger` restates in core), `packages/pds/src/context.ts:10,19,25` (`PdsLogger`/`PdsPorts`/`PdsContext` — the existing precedent, untouched by this task), `packages/core/src/index.ts:22-23` (the barrel; `./plugin.js` sorts between `./config.js` and `./ports.js`), `packages/cli/src/context.test.ts:65` (end of file — where the composition test goes)

## Steps

- [ ] Create `packages/core/src/plugin.ts` opening with a module comment stating that it owns the plugin SPI vocabulary, that a plugin depends on `blogwright-core` and never on the CLI, and that the CLI's `OpsContext` is deliberately wider than what a plugin is handed.
- [ ] Declare `PluginLogger` with `info`/`step`/`ok`/`warn`/`error` (the shape `packages/cli/src/logger.ts:9` already has and `packages/pds/src/context.ts:10` duplicates) and `PluginPorts` with `fs: FileSystem` and `terminal: Terminal` from `packages/core/src/ports.ts:12,34` — the two shared ports core owns and the only two a plugin may cross. `PluginPorts` is a separate declaration rather than the CLI's `Ports` (`packages/cli/src/ports.ts:25`) because the rest of that interface is CLI-private and core cannot name it: `vcs` (`:9`) and `ping` (`:21`) are declared in the CLI, and tasks 05 and 06 add `loader` and `packages` there too.
- [ ] Declare `SiteState` as `{ readonly resources: Readonly<Record<string, ResourceOutputs>> }` over `ResourceOutputs` (`packages/core/src/state.ts:3`), the read-only view of the site's recorded resource outputs; `OpsState` (`state.ts:5`) satisfies it because a mutable property is assignable to a `readonly` one, so the CLI needs no wrapper object.
- [ ] Declare `PluginContext<TConfig>` — generic over the config block the plugin owns — with exactly `env`, `domain`, `preview`, `config: OpsConfig`, `pluginConfig: TConfig`, `names: Names`, `accountId`, `clients: AwsClients`, `ports: PluginPorts`, `tags`, `logger: PluginLogger`, `store: StateStore` (the plugin's own scoped store, from task 04), `state: OpsState` (the plugin's own state, loaded from its scoped store), `siteState: SiteState` (the read-only site view), `record(nodeId, outputs)` and `save()` — and nothing else; `agentDir` (`packages/cli/src/context.ts:40`) stays CLI-internal. Every member is required except `tags`, declared `tags?: Record<string, string> | undefined` under `exactOptionalPropertyTypes` — the shape `PdsContext` already has (`packages/pds/src/context.ts:33`). A required `tags` would propagate through task 24's `Pick` and break `createTestContext` (`packages/pds/src/test-support.ts:96-108`), which supplies none; the CLI always has one to give (`packages/cli/src/context.ts:45`), so nothing is lost.
- [ ] `pluginConfig` carries the block `validateConfig` returned (task 03), because `ctx.config.<key>` cannot compile: `OpsConfig` (`packages/core/src/config.ts:68`) has no index signature, so reading a plugin's key off it is `TS2339` under this repo's strict settings, and the only escapes — a cast or `any` — are banned by DEVELOPMENT.md §Code style.
- [ ] `save()` is on the context, not CLI-internal: `applyGraph` calls `ctx.save()` after every node (`packages/cli/src/graph.ts:84`), so a plugin graph reconciled through the same engine needs it.
- [ ] Declare `record(nodeId: string, outputs: ResourceOutputs): void` on `PluginContext` as the ONLY way a plugin's resource nodes record outputs, writing into the plugin's own `state`. Doc-comment it against `packages/cli/src/nodes.ts:20-22` (the private `output(ctx, id)` helper it mirrors) and state the rule it exists to enforce: a node must never call `store.save()` itself, because `applyGraph` (`packages/cli/src/graph.ts:84`) saves the in-memory state after every node and would clobber a direct write with stale data.
- [ ] Type `state` as core's own `OpsState` (`packages/core/src/state.ts:5` — `{ version, env, updatedAt, resources }`), NOT as a bare `Record<string, ResourceOutputs>`. The engine reaches through it: `destroyGraph` does `delete ctx.state.resources[node.id]` (`packages/cli/src/graph.ts:94`), which against a map that *is* the outputs raises `TS18048: 'ctx.state.resources' is possibly 'undefined'`. `state` is therefore the site's state type with a mutable `resources`, and `SiteState` is the same shape with `resources` readonly — distinct types, because tasks 48/50/51 write through the former while task 53 reads the latter, and conflating them is the defect this task exists to prevent.
- [ ] Doc-comment every exported symbol and every `PluginContext` field with what a plugin may rely on, naming the load-bearing consumers: `names.deliverySource` (`packages/core/src/config.ts:343`) and the site's recorded distribution outputs feed the analytics log-delivery node in task 53, and `accountId` builds the analytics IAM role ARNs.
- [ ] Add `export * from './plugin.js';` to `packages/core/src/index.ts` in the barrel's alphabetical position, between `./config.js` (:22) and `./ports.js` (:23).
- [ ] Add the compile-time proof at the end of `packages/cli/src/context.test.ts`, and make it the *composition* rather than a bare assignment: a `createTestContext()` result is NOT assignable to `PluginContext` — `OpsContext` (`packages/cli/src/context.ts:25-51`) carries thirteen of the sixteen members but none of `pluginConfig`, `siteState` or `record`, so `const p: PluginContext = createTestContext()` is `TS2739: Type 'OpsContext' is missing the following properties from type 'PluginContext<never>': pluginConfig, siteState, record`. The test therefore spreads an `OpsContext` and supplies exactly those three — the shape task 10's dispatch-boundary adaptation builds for real — annotates the result `PluginContext<unknown>` imported from `blogwright-core` with no cast and no `any`, and asserts one field so the test has a runtime body as well as a type-level one. It fails the build if `PluginContext` grows a member neither `OpsContext` nor the boundary supplies, which is the alarm this task exists to install.

## Definition of done

- [ ] `PluginContext<TConfig>` names exactly `env`, `domain`, `preview`, `config`, `pluginConfig`, `names`, `accountId`, `clients`, `ports`, `tags` (the one optional member, `tags?: Record<string, string> | undefined`), `logger`, the plugin's own scoped `store`, `state`, `siteState`, `record()` and `save()` — and nothing more, matching the spec's enumeration field for field. What stays CLI-side is recorded in the module's doc comments, and stated as the rule rather than a count: `agentDir` (`packages/cli/src/context.ts:40`), and every member of the CLI's `Ports` (`packages/cli/src/ports.ts:25`) beyond `fs` and `terminal` — `vcs`, `ping`, and the `loader`/`packages` ports tasks 05 and 06 add — because core cannot name a CLI-private type.
- [ ] A type-level test proves `pluginConfig` is what a plugin reads: a `PluginContext<{ foo: string }>` exposes `ctx.pluginConfig.foo` with no cast, while `ctx.config` has no such key.
- [ ] `state` and `siteState` are separate fields of separate types, and a test proves the distinction: a `ResourceNode<PluginContext>` calls `ctx.record('n', { arn: 'a' })`, the value is readable back from `ctx.state.resources`, and `ctx.siteState` is unaffected. A second test proves `state` is an `OpsState` rather than a bare outputs map by running the real `destroyGraph` over a one-node plugin graph and asserting `ctx.state.resources` no longer carries the id — the shape the engine requires. Without these the two fields drift back together at task 16.
- [ ] `names`, `accountId` and the site-state view are justified in doc comments by their actual consumers (task 53's log-delivery node reading `names.deliverySource` and the site's distribution outputs; the analytics IAM roles reading the account id), so a later reader cannot mistake them for speculative surface, and every exported symbol carries a doc comment (DEVELOPMENT.md §Documentation).
- [ ] `siteState` is `readonly` in the type, so `ctx.siteState.resources['x'] = {}` does not typecheck and a plugin can never write `state/<env>.json` — `record()` into the plugin's own scoped state is the only state surface it may write through; `packages/core/src/plugin.ts`'s import list names only core modules (`./clients.js`, `./config.js`, `./ports.js`, `./state.js`) and no CLI or pds module, and `packages/pds/src/context.ts` is untouched, because narrowing `PdsContext` is task 24.
- [ ] A test in `packages/cli/src/context.test.ts` builds a `PluginContext<unknown>` from a `createTestContext()` result plus exactly `pluginConfig`, `siteState` and `record` — no cast, no `any`, no field written twice — so the composition claim fails the build if it stops holding. The three supplied members are named in a comment as the dispatch boundary's contribution, and `OpsContext` supplying the other thirteen is what the test proves; a bare assignment is NOT the gate, because `OpsContext` does not satisfy `PluginContext` and never will.
- [ ] Meets the repo definition of done (see plan.md baseline).
- [ ] Reviewable: run `pnpm build && pnpm test -- context`, then add to `PluginContext` a field neither `OpsContext` nor the boundary supplies and confirm `pnpm typecheck` fails inside `packages/cli/src/context.test.ts` — the composition is a real gate, not a comment. Then confirm the negative half by hand: `const p: PluginContext = createTestContext()` must fail with `TS2739` naming `pluginConfig`, `siteState` and `record`, which is why the gate is a composition.
