# Task 19 - Validate plugin-owned config blocks through each plugin

**Plan:** [plan.md](../plan.md) · **Certificate:** [19-cli_plugin_config_validation-certificate.md](19-cli_plugin_config_validation-certificate.md)

**Implements:** [2026-07-26-cli_plugin_system.md §CLI → Config ownership (Add)](../../../changes/2026-07-26-cli_plugin_system.md) ("the CLI reads the plugin's block out of the raw document `parseConfigDocument` returns and calls that plugin's `validateConfig` on it. ## Steps

- [ ] Validate ONLY the plugin being dispatched, in the dispatch path - not in `createContext`. Record the choice and its reason in the module comment of `packages/cli/src/plugins.ts`. `createContext` (`packages/cli/src/context.ts:110-124`) is the path every built-in command takes and accepts no plugin list, so validating there would run discovery on `deploy`/`status`/`bootstrap` - breaking task 10's laziness test and this task's own DoD - and there is no seam through which the dispatched plugin alone could be reached.
- [ ] Thread the raw document from the file to the dispatcher, because nothing does today: change `loadConfig` (`packages/cli/src/context.ts:85-102`) to call task 03's `parseConfigDocument` and return `{ config, raw }`, and have `createContext` keep the raw half on `OpsContext` as `configDocument: Readonly<Record<string, unknown>>`. `createContext` is the only place the config file is read, and `runPlugin` is where a plugin's block is needed, so without this field the dispatcher would have to re-read and re-parse the file. The field is CLI-side and does not join `PluginContext` - a plugin reads `pluginConfig`, never the document - so `createTestContext` gains it and nothing else moves.
- [ ] Add `resolvePluginConfig(plugin, configDocument)` in `plugins.ts` taking ONE plugin and the raw document (not the `OpsConfig`, which has no index signature): when the plugin declares both `configKey` and `validateConfig`, read the block with `pluginBlock(configDocument, configKey)` (task 03) and pass it to the validator, RETURNING the resolved block for the dispatcher to place on `ctx.pluginConfig`. When the key is absent, or the plugin declares no `configKey`, return an empty object rather than `undefined` - `pluginConfig` is a required member and DEVELOPMENT.md's no-null rule forbids the alternative; a plugin owning no `configKey` is a `Plugin<never>` and cannot read it anyway.
- [ ] Call it from `runPlugin` (task 10) as part of the `toPluginContext` adaptation, before the plugin's `run`, so `pluginConfig` is the validator's return rather than the `{}` placeholder task 10 left there, an invalid block fails before the command does any work, and a valid one is typed for the plugin. Built-in commands never reach it.
- [ ] Wrap a plugin's thrown error so the plugin's own message survives verbatim with a prefix naming the plugin, and let it exit non-zero through the existing `bin.ts` error path.
- [ ] Add the duplicate-`configKey` rejection beside task 09's duplicate-namespace check, with an error naming both packages and the shared key.
- [ ] Extend `packages/cli/src/context.test.ts` with fake plugins only - block present, block absent, block for an uninstalled plugin, a failing validator, and two plugins claiming one key - plus an assertion that a built-in command loads no plugin modules, and one that `loadConfig`'s `raw` carries a top-level key `OpsConfig` does not declare while `config` is unchanged from today.

## Definition of done

- [ ] `loadConfig` returns `{ config, raw }` and `createContext` puts `raw` on `OpsContext` as `configDocument`, so the dispatch path reaches a plugin's block without re-reading the file - a test asserts a key no `OpsConfig` field declares survives onto `configDocument`, and that `config` is byte-identical to what `parseConfig` returns today.
- [ ] The dispatched plugin, when it declares both `configKey` and `validateConfig`, is called with that key's raw block read off `configDocument`, and is **also called with `undefined` when the block is absent** (CORRECTED 2026-08-30 - the original text here said the validator "is not called at all when the block is absent" and that `pluginConfig` is `{}` on that path; task 44's gate proved that now breaks). A validator is the only thing that can turn an absent block into the plugin's own defaults, and `blogwright <plugin> <action>` on a repo with no block for that plugin is a configuration the analytics module's own doc calls valid. With the raw `{}` placeholder instead, `resolveAnalyticsConfig` raises a bare `TypeError: Cannot read properties of undefined (reading 'tableBucket')` - verified by execution against the built `dist` - and every literal default is `undefined` at runtime while typed as total, which is worse than the throw. Nothing catches either: the CLI dispatches over `Plugin<unknown>` and `toPluginContext(ops): PluginContext<unknown>` (`plugin-commands.ts:241,466`), so `TConfig` is erased exactly where the placeholder is injected, and task 47 binds the validator verbatim so no wrapper seam absorbs it. `validateAnalyticsConfig` already accepts `undefined` and returns a fully-defaulted block, so this is the shape the plugin expects. `pluginConfig` is still an empty object rather than `undefined` on the **no-`configKey`** path, where there is no validator to call - one test each for: block present, block absent (validator called with `undefined`, defaults applied), and no `configKey` at all.
- [ ] A config file carrying a block for a plugin that is not installed parses, is inert, and the key survives on the config object (test) - the same contract `pds` has today; this task changes nothing in `packages/core/src/config.ts`, so core still validates the `pds` block and task 27 has somewhere to hand that validation to.
- [ ] A plugin's validation failure surfaces the plugin's own message unchanged, prefixed with enough context to name the plugin, and exits non-zero; and two plugins declaring the same `configKey` is rejected with an error naming both - one negative test each, asserting on the message.
- [ ] The scope of validation - every discovered plugin versus only the plugin being dispatched - is chosen, stated in a module comment and consistent with the laziness rule, with a test asserting context-taking built-ins - `deploy`, `bootstrap` and `status` among them - still load no plugin modules; the choice is recorded plainly because task 28 has to reason about it.
- [ ] Meets the repo definition of done (see plan.md baseline).
- [ ] Reviewable: run `pnpm --filter blogwright exec vitest run context --reporter=verbose`; confirm the failing-validator case fails before any AWS client call is made (the test's fake STS records no `getAccountId`) and that the uninstalled-plugin block is still readable on the returned `config`.
