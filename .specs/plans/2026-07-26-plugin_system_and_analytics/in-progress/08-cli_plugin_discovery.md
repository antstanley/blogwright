## Steps

- [ ] Create `packages/cli/src/plugins.ts` with a module comment stating what it owns and recording the collect-versus-throw choice: a broken plugin is a reported failure, not an aborted CLI run, because one bad dependency must not make `blogwright deploy` unusable.
- [ ] Implement `discover(repoRoot, cliPackageDir, ports)` returning a value type carrying `plugins` and `failures` - both always arrays, never `null` or `undefined` - where each failure names the package and the reason.
- [ ] Read `<repoRoot>/package.json` through `ports.fs.readText` and parse it, raising an error naming the path and what would fix it when the file is absent (`FileNotFoundError`) or unparseable, before any candidate is resolved.
- [ ] Resolve every candidate's `package.json` by resolving the BARE specifier through `ports.loader.resolve` and walking up from the resolved file to the nearest `package.json` **that carries a `name`** - add that guard to task 05's `packageJsonPathFor` in `packages/cli/src/adapters/node-module-loader.ts` as part of this task, and cover it with a fixture. Task 05's gate proved the unguarded walk stops at a dual-package `dist/package.json` (`{"type": "module"}`, no `name`, no `blogwright` field), so discovery skips a valid installed plugin SILENTLY - no error, no failure entry, its commands simply missing from `blogwright --help`. The spec's §Plugin discovery now states the qualifier. Never resolve `<name>/package.json` directly: a package whose `exports` map does not list `./package.json` makes that throw `ERR_PACKAGE_PATH_NOT_EXPORTED` under Node's exports encapsulation, which is the case for every published package here. Verified 2026-07-26 - `require.resolve('blogwright-pds/package.json')` throws today while `require.resolve('blogwright-pds')` resolves. Give `ModuleLoader` a `packageJsonPathFor(specifier, fromDir)` operation (task 05) so the walk-up lives in the adapter, not in domain code.
- [ ] Build the consumer half of the candidate set from every `dependencies` and `devDependencies` name starting with `blogwright-`, resolved with `fromDir = repoRoot`.
- [ ] Build the bundled half WITHOUT the resolver: locate the CLI's own package root by walking up from `import.meta.url` to the nearest `package.json` - the precedent is `agentDir` at `packages/cli/src/context.ts:118` - read it through `ports.fs`, and fold its `blogwright-*` dependencies (`packages/cli/package.json:26-30`) into the candidate set, each resolved with `fromDir = <the CLI package directory>`. Do NOT resolve the bare specifier `blogwright`: verified 2026-07-26, both `require.resolve('blogwright')` and `require.resolve('blogwright/package.json')` throw `ERR_PACKAGE_PATH_NOT_EXPORTED` from a consumer root, because `packages/cli/package.json` declares an `exports` map with a `./rkey` entry and no `.` entry - the CLI is consumed through its `bin`. Resolving `blogwright-pds` from `repoRoot` fails too: under pnpm the consumer's `node_modules` holds only the `blogwright` symlink. Because `import.meta.url` is a composition-root concern, the self-location lives beside the other adapter wiring, not inside `plugins.ts`, and is passed in. Give it a name and a home in this task rather than leaving each caller to re-derive it: export `cliPackageDir(): string` from `packages/cli/src/context.ts` beside the `agentDir` resolution at `:118`, as a standalone function and NOT inside `createContext` - task 17 dispatches `blogwright plugin list` before a context exists and still needs the value. Tasks 10, 11, 14 and 17 are its four callers; without an owner here, `discover`'s second argument has no supplier and each of them invents one.
- [ ] For each candidate, read the resolved `package.json` through `ports.fs`: skip silently when there is no `blogwright.plugin` field, record a failure naming the package when the field is malformed (wrong type, or a namespace violating `^[a-z0-9-]+$`), and otherwise `ports.loader.load` the package and pass its default export through core's `validatePlugin`, recording the validator's reason as the failure when it rejects.
- [ ] Add ONE integration test that uses the REAL `ModuleLoader` adapter against this workspace and discovers `blogwright-pds` from the CLI package directory - no map-backed fake. The map-backed fake cannot model exports encapsulation, so without this test the whole discovery path passes CI and fails for every real install. This test is a precondition of task 29, which deletes `runPds` and makes discovery the only route to `blogwright pds <action>`.
- [ ] Write `packages/cli/src/plugins.test.ts` over `createMemoryFileSystem` and a map-backed `ModuleLoader` fake, covering the absent and unparseable `package.json`, the non-matching dependency, the bundled plugin, the missing manifest field, the malformed manifest, and the failing default export.

## Definition of done

- [ ] `<repoRoot>/package.json` is read through `ports.fs` and an absent or unparseable file raises an error naming the path and what would fix it (negative tests); both `dependencies` and `devDependencies` are considered, and only names starting with `blogwright-` become candidates - a test with a non-matching dependency proves it is never resolved through the loader.
- [ ] The candidate set is the UNION of the consumer's `blogwright-*` deps, resolved from `repoRoot`, and the CLI's own `blogwright-*` deps, resolved from the CLI package directory located via `import.meta.url` - verified against this repo, whose root `package.json` has zero `blogwright-*` entries, so a consumer-only scan finds nothing and `blogwright pds` would break at task 29. Neither the bare specifier `blogwright` nor `blogwright/package.json` is ever handed to the resolver: both throw `ERR_PACKAGE_PATH_NOT_EXPORTED`, and a test asserts the resolver was not called with either. A test proves a bundled plugin is discovered from a consumer `package.json` that lists only `blogwright`, because a consuming repo depends on `blogwright`, not on `blogwright-pds`, and `blogwright pds sync` must keep working for every user once task 29 deletes `runPds`.
- [ ] A candidate whose `package.json` has no `blogwright.plugin` field is skipped silently with no error and no load (the test asserts the loader's `load` was not called for it); a candidate whose manifest field is malformed (wrong type, or a namespace violating `^[a-z0-9-]+$`) and a candidate whose default export fails `validatePlugin` are each reported as a load failure naming the package and carrying the reason.
- [ ] `discover` returns a value type carrying loaded plugins and failures with no `null`/`undefined` for either collection, the collect-versus-throw choice is stated in the module comment, and the module imports only ports and core - no `node:fs`, no `node:module` - as `pnpm lint` verifies.
- [ ] `cliPackageDir()` is exported from `packages/cli/src/context.ts`, resolves from `import.meta.url` the way `agentDir` does at `:118`, and is callable without a context - a test asserts it returns the directory holding the CLI's own `package.json`. `plugins.ts` never reads `import.meta.url` itself (`grep -n "import.meta" packages/cli/src/plugins.ts` returns nothing), and every caller passes this one value, so the second argument has exactly one source.
- [ ] Meets the repo definition of done (see plan.md baseline).
- [ ] The walk up stops at the nearest `package.json` **carrying a `name`**, not merely the nearest one: a fixture published as a dual-package layout (`exports: {".": "./dist/index.js"}` plus `dist/package.json` of `{"type": "module"}`) is discovered as a plugin, and a test asserts it - because without the guard it is skipped silently, which is the failure mode with no signal at all. The guard lives in `packageJsonPathFor` so every caller of the port inherits it.
- [ ] Candidate `package.json` files are located by resolving the bare specifier and walking up, never by resolving `<name>/package.json`; one integration test using the real `ModuleLoader` adapter discovers `blogwright-pds` from this workspace and passes. Reviewable: temporarily change the resolver to `<name>/package.json` and confirm that integration test fails with `ERR_PACKAGE_PATH_NOT_EXPORTED` while every fake-backed test still passes - that gap is exactly what the integration test exists to close.
- [ ] Reviewable: run `pnpm --filter blogwright exec vitest run plugins --reporter=verbose`; confirm every unit case runs against `createMemoryFileSystem` and a map-backed `ModuleLoader` fake with no disk or registry access, that the one integration case is clearly marked as using the real adapter, and that the bundled-plugin case passes with a consumer `package.json` whose only dependency is `blogwright`.
