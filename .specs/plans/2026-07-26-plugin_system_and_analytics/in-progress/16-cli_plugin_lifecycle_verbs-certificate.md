## Residue

Notes for the validator, not obligations: the spec settles `blogwright destroy` against live plugin state by refusing (§State → Scoped state stores), which O5 discharges - what remains open, and is carried forward at task 20, is whether `plugin remove` should offer to run the plugin's teardown first; the analytics change spec declares its own `bootstrap`/`status`/`destroy`, so task 47's command table must be re-read against whatever precedence this task fixed; and whether a plugin verb should run when the site itself has never been bootstrapped is not covered by the DoD.

Three findings raised by this validation, none of them a breach of an obligation above, all carried forward:

1. `previewTeardown` (`packages/cli/src/commands.ts:290`) runs the same `destroyGraph(buildNodes(ctx), ctx)` and therefore the same `bucketNode.delete()` → `deletePrefix(bucket, '')`, but is NOT guarded. A plugin bootstrapped into the `preview` environment (`blogwright <plugin> bootstrap preview`, which `runPlugin`'s env resolution allows) writes `state/preview.<plugin>.json` into the preview bucket, and `blogwright preview teardown --yes` then deletes it while the plugin's resources live on - the exact orphaning O5 exists to prevent. The task scoped the guard to `commands.ts:54` only, so this is out of contract, but it is a live hole.
2. `renderActions` (`plugin-commands.ts:412`) lists a plugin's declared commands plus the generic `init`, but not the three new generic lifecycle verbs. A nodes-only plugin that declares no commands therefore prints `"demo" actions:` and nothing at all on an unknown action (confirmed by execution), even though `bootstrap`/`status`/`destroy` all work on it - the outcome that function's own doc comment calls "worse than no refusal", and the reason task 13 added `init` to it. `cli.ts`'s `renderPluginSection` has the same omission in `--help`.
3. `assertNoScopedState` runs before `clearRunningMicrovms` and before any node delete, and `S3Client.listObjects` does not swallow a 404 the way `getObjectText` does. `blogwright destroy --yes` against an environment whose bucket is already gone now fails at the guard with a raw `NoSuchBucket` and deletes nothing, where before it deleted the eight non-bucket resources first and then failed at the bucket node. Arguably the safer behaviour, but it is an undocumented, unpinned change to a recovery path.

Minor test-hygiene note: `cli.test.ts`'s and `plugin-commands.test.ts`'s context factories now default `clients.s3.getObjectText` to resolve `undefined` for every context they build, loosening `createTestContext`'s reject-everything default for all tests using them, not only the plugin-dispatch ones. Both are documented in place.
